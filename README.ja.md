# MLB ポストシーズン サマリーサイト

[English](README.md) | **日本語**

**MLB ポストシーズンのグラフィカルなサマリー**に、任意のシリーズの
**AI による勝敗予測**を加えた、軽量なサーバーレス Web アプリです。
すべて TypeScript で実装し、AWS CDK によってワンコマンドで AWS へデプロイできます。

このプロジェクトは [Kiro University Challenge](https://kiro.dev/2026/university/)
最終試験への提出作品です。

> **審査員の方へ:** 7 つの必須レッスンと 2 つのボーナスをそれぞれどのように実証しているか、
> および関連ファイルへのリンクは [DEMONSTRATED_LESSONS.md](./DEMONSTRATED_LESSONS.md)（実証された教訓）
> を参照してください。

## 概要

- **シーズンセレクターによる複数シーズン対応** — アプリは年度を認識します。現在の年は
  **2026 年**で、セレクターは **2024・2025・2026**（デフォルトは 2026）を選べます。過去の
  シーズン（2024・2025）は**結果のみ**で、現在のシーズン（2026）がライブで進行中のものです。
- **グラフィカルなポストシーズン表示** — ワイルドカードラウンドからワールドシリーズまでの
  ブラケットを表示し、各シリーズ・両チーム・シリーズスコア・ステータスを示します。
- **シリーズ詳細** — シリーズごとの試合単位の結果（すべてのシーズンで利用可能）。各試合を展開すると、
  イニングごとのラインスコア（R/H/E）、勝利/敗戦/セーブ投手、球場、そして存在する場合はリキャップ/
  ハイライトのリンクを表示する**試合ごとのアコーディオン**を備えています。
- **順位 / サマリーパネル** — 参加チームをリーグ別にまとめ、ポストシーズンの進行状況を表示します。
- **勝敗予測（追加機能、現在のシーズンのみ）** — 進行中シーズンのシリーズについて、優勢チーム・
  勝率・そして選定理由を説明する **AI 生成のナラティブ**を表示します。予測機能は**現在（進行中）
  のシーズンのみ**で提供され、完了したシーズンは最終結果のみを表示します。

数値の勝率はコード内の決定論的モデルで算出され（説明可能でユニットテスト済み）、
**Amazon Bedrock** が**選択可能なモデル**（**Amazon Nova** ファミリー、デフォルトは
**Nova Lite**。**Anthropic Claude** も利用可能）でそれを文章に変換し、ナラティブは
**UI 言語（EN / JA）にローカライズ**されます。

- **ダークモードとアクセシビリティ** — OS の設定に追従する**システム / ライト / ダーク**のテーマ
  切り替え（`localStorage` に保存）、両テーマでの WCAG AA コントラスト、チームバッジ文字色の自動調整、
  ブラケットの完全な**キーボード操作**、そして**スクリーンリーダー向けラベル**を備え、ライトとダークの
  両方で自動の **axe** チェックにより検証されています。

- **お気に入りチーム** — 1 つ以上のチームをお気に入りに登録でき（`localStorage` に保存）、
  そのシリーズは**色だけに頼らない**手がかり（星アイコン＋独自のボーダー＋スクリーンリーダー向け
  ラベル）でブラケット上に強調表示されます。ヘッダーのピンが各お気に入りの状況を要約し、ファイナルで
  敗れたチームは **敗退 / Eliminated** 表示に切り替わります。お気に入りのチームだけを表示する
  フィルターもあります。EN / JA 対応。

認証はありません。公開・読み取り専用です。賭け事を目的とした製品ではありません。

## アーキテクチャ

![Architecture](docs/architecture.png)

編集可能な図は [`docs/architecture.drawio`](docs/architecture.drawio)（draw.io /
diagrams.net で開けます）です。ベクター形式のエクスポート
[`docs/architecture.svg`](docs/architecture.svg) と PNG（`docs/architecture.png`）も含まれています。

- **フロントエンド:** React + TypeScript（Vite）。**S3**（プライベート、Origin Access
  Control）にホストし、**CloudFront** 経由で配信します。
- **バックエンド:** **API Gateway HTTP API**（CORS 付き）の背後にある 3 つの **AWS Lambda**
  関数（Node 20）。ルート: `GET /bracket`、`GET /prediction`、`POST /prediction`、
  `GET /game`。Bedrock を呼ぶのは予測関数だけで、試合詳細関数は DynamoDB と公開 MLB API
  のみを使用します。
- **データ:** **DynamoDB** がシーズンごとに集約済みブラケット JSON・レギュラーシーズン勝率・
  試合ごとの詳細をキャッシュします（単一テーブル、`pk` でキー管理）。
- **AI:** **Amazon Bedrock**（`InvokeModel`）が、選択可能なモデル（Amazon Nova
  micro/lite/pro、デフォルトは Nova Lite。Anthropic Claude も利用可能）から、UI 言語に
  ローカライズした予測ナラティブを生成します。
- **IaC:** **AWS CDK（TypeScript）**がワンコマンドデプロイ用にすべてをプロビジョニングします。

## MLB データ戦略

1. **まず DynamoDB キャッシュ。** `getBracket` は DynamoDB の `pk = BRACKET#<season>` を
   参照します。鮮度のあるキャッシュ済みブラケット（`ttl` 属性による TTL、約 15 分）はそのまま返されます。
2. **キャッシュミス時に MLB Stats API。** Lambda が公開 MLB Stats API
   （`https://statsapi.mlb.com/api/v1/schedule/postseason?sportId=1&season=YYYY`、API キー不要）
   を取得し、試合をシリーズに集約してキャッシュへ書き戻します。
3. **シードフォールバック（完了シーズン）。** ライブ API に到達できない場合は、同梱の
   `@mlb/shared` シードデータセットを使用し、テストやデモで決定論的に動作し続けます。
   フォールバックは **2024 と 2025 の両方**をカバーします:
   - `postseason-2024.json` — ドジャースがヤンキースを 4-1 で破る。
   - `postseason-2025.json` — ドジャースがブルージェイズを 4-3 で破る（ライブ MLB Stats API
     から集約した実際の結果）。

   フロントエンドもブラケットリクエストが失敗した場合はこれらのシードにフォールバックするため、
   オフラインでもデモが描画されます。
4. **2026 がライブ / 現在のシーズン。** 現在の年（2026）には同梱シードがなくライブ取得されます。
   アプリは空の、またはまだ始まっていない 2026 ポストシーズンを適切に処理し（壊れたブラケットの
   代わりに「まだ開始していません」というメッセージを表示）、集約処理はライブスケジュールが返す
   未確定ラウンドのプレースホルダーチームを許容します。

### シーズンと予測機能

シーズンセレクターは 2024・2025・2026（デフォルト 2026）を提供します。現在の年より厳密に前の
シーズンは**結果のみ**です。予測 UI は非表示になり、`/prediction` エンドポイントは数値予測の
代わりに結果のみのレスポンス（`mode: 'results'`）を返します。現在のシーズン（2026）は**予測可能**
なので、進行中のシリーズに対して予測機能が提供されます。`/prediction` は開始済みシリーズには
`mode: 'prediction'` を、まだ始まっていないシリーズには `mode: 'upcoming'` を返します。すべての
バリアントは HTTP 200 で返され、フロントエンドは `mode` で分岐します。

### 進行中シーズンのライブ自動更新

現在の進行中シーズンにライブのシリーズがある間、ブラケットはページ再読み込みなしで
バックグラウンドで最新の状態に保たれます。ブラケットの `updatedAt` から導いた
ローカライズされた**「最終更新」**の相対時刻（例: 「最終更新: 2分前」/「Last updated:
2 minutes ago」）と、いつでも押せる手動の**更新**ボタン（更新中は「更新中…」表示で
無効化）を表示します。自動更新は意図的に範囲を絞っています:

- **現在の進行中シーズンに対してのみポーリング**します — 具体的には、予測可能なシーズン
  （`CURRENT_YEAR`）で、ブラケットに少なくとも 1 つの `in_progress` シリーズがある場合です。
  結果のみのシーズン（2024・2025）や、ライブのシリーズがない予測可能なシーズンではポーリング
  しません。これらでも最終更新の行と手動の更新ボタンは表示されますが、自動のバックグラウンド
  取得は走りません。
- 間隔は文書化された **60 秒**（`AUTO_REFRESH_INTERVAL_MS`）で、バックエンドのブラケット
  キャッシュ TTL（約 15 分）を十分に下回るため、ポーリングが実際に変化し得るデータを追い越す
  ことはありません。
- **タブが非表示のときは一時停止**し（Page Visibility API）、タブに戻ると即座に再取得して
  再開します。
- 更新は**ちらつきがありません**。ブラケットはマウントされたまま（スクロール位置と選択中の
  シリーズは保持）で、フルの読み込み画面が点滅することはありません。更新に失敗した場合は、
  フルのエラーページではなく小さく控えめな通知を出しつつ、直前に読み込んだデータを画面に
  残します。

この機能はフロントエンドのみで、`frontend/src/relativeTime.ts`・
`frontend/src/useAutoRefresh.ts`・`frontend/src/pages/HomePage.tsx` にあります。

### レギュラーシーズン勝率が予測を駆動

予測は、シリーズの進行度と各チームの**実際のレギュラーシーズン勝率**をブレンドします。
予測の際、バックエンドは MLB Stats API の順位表
（`https://statsapi.mlb.com/api/v1/standings?leagueId=103,104&season=YYYY`）を取得し、
純粋でユニットテスト済みの関数でチームごとの勝率マップに集約してモデルに渡します。この
マップはシーズンごとに **DynamoDB にキャッシュ**され（`pk = STANDINGS#<season>`、
ブラケットキャッシュと同じ約 15 分の TTL。テーブルは単一パーティションキーのためインフラ変更は
不要）。順位表の取得・解析・集約が何らかの理由で失敗した場合、モデルは該当チームを**中立の
0.5** にフォールバックし、**それでも予測を返します**。したがって順位表の障害が予測をエラーに
変えることはありません。`mode: 'prediction'` レスポンスには追加の `metrics` オブジェクト
（各チームの勝率）が含まれ、予測パネルはローカライズされた**「予測の根拠」**ブロックで各チームの
レギュラーシーズン勝率（不明な場合は「データなし」）を表示するため、根拠を説明できます。現時点で
配線されているのは勝率シグナルのみで、ピタゴラス（得失点差）や直近 10 試合のシグナルはありません。

### 予測キャッシュとコスト制御（Issue #23）

`/prediction` は認証なしの公開エンドポイントで、課金対象の分岐が Amazon Bedrock を
呼び出すため、同じ状況に対する再リクエストはキャッシュし、リクエストレートに上限を設けています。

- **キャッシュ対象。** 保存されるのは `mode: 'prediction'` レスポンスのみです。Bedrock を
  呼ばない 3 つのショートサーキット（結果のみシーズン、`final` のシリーズ、未解決または
  未開始のシリーズ）はキャッシュより前に位置し、キャッシュされません。
- **キャッシュキー。** DynamoDB のパーティションキーは
  `PREDICTION#<seriesId>#<highWins>-<lowWins>#<language>#<modelId>#<accuracy>` で、
  シリーズの状況とナラティブの各設定でキー管理されます。未指定の `accuracy` はキー生成前に
  モデルのデフォルト（`0.5`）に解決されるため、省略リクエストと明示的な `0.5` は同一の安定した
  キーに対応します。キャッシュはブラケットキャッシュと同じ単一 `pk` の DynamoDB テーブル上に
  あるためインフラのスキーマ変更は不要で、`TABLE_NAME` が未設定のときは no-op です。
- **再リクエストは Bedrock をスキップ。** 同じ状況に対する 2 回目のリクエストはキャッシュ
  ヒットとなり、予測モデルの実行や Bedrock の呼び出しをせずに保存済みレスポンスを返します。
- **シリーズ進行による無効化。** `highWins-lowWins` がキーの一部であるため、試合結果（いずれ
  かのチームの勝利数の変化）によって異なるキーが生成され、実質的にキャッシュが無効化されて、
  新しい予測と新たな Bedrock 呼び出しが行われます。
- **TTL のバックストップ。** 各キャッシュ済み予測は数値の `ttl` として **15 分**
  （`PREDICTION_TTL_SECONDS`）を持ちバックストップとして機能します。主たる無効化メカニズムは
  勝利数をキーに含める設計です。
- **リクエストのスロットリング。** HTTP API のデフォルト（`$default`）ステージは、定常
  **毎秒 20 リクエスト**、バースト **40**（`ThrottlingRateLimit` / `ThrottlingBurstLimit`）に
  スロットリングされており、公開エンドポイントが暴走した Bedrock コストに陥る速度に上限を設け
  つつ、通常の閲覧パターンを十分に上回る水準に保ちます。`infra/test/stack.test.ts` がこの正確な
  値をアサートします。
- **CloudWatch メトリクス（EMF）。** キャッシュとコストのメトリクスは Embedded Metric
  Format（EMF）の標準出力ログ行で出力されるため、`cloudwatch:PutMetricData` の IAM 付与も、
  リクエスト経路での追加の AWS SDK 呼び出しもありません。名前空間は
  **`MlbPostseason/Prediction`**、メトリクス名は **`PredictionCacheHit`**・
  **`PredictionCacheMiss`**・**`BedrockInvokeCount`**（ヒット時は 0、ミス時は 1）です。
  seriesId は高カーディナリティのディメンションではなく、通常のログプロパティとして保持します。

実装は `backend/src/service/predictionCacheKey.ts`（純粋なキー関数）・
`backend/src/store/dynamo.ts`（`getCachedPrediction` / `putCachedPrediction` と
`PREDICTION_TTL_SECONDS`）・`backend/src/service/bracketService.ts`
（キャッシュ優先の配線）・`backend/src/metrics/emf.ts`（EMF ヘルパー）・
`infra/lib/mlb-postseason-stack.ts`（スロットリング）にあります。

### モデル精度 / バックテスト

クライアントサイドの**モデル精度**ページ（`/accuracy`。すべてのシーズンでヘッダーの
ナビゲーションリンクから到達可能）は、決定論的な予測モデルが**完了した** 2024・2025 年
ポストシーズンをどれだけ正しく当てられたかを表示します。これは `@mlb/shared` にある純粋で
決定論的な**バックテストエンジン**が、収録済みシードブラケットをアプリと同じ `predict()` で
再生することで実現しています。

- **決定論的・シードのみ。** エンジンは純粋な共有コードと収録済みシード JSON（2024 /
  2025）だけをインポートします。ページはすべてブラウザー内で**クライアントサイド**で算出し、
  **バックエンドのエンドポイントもインフラの変更もありません**。そのため数値は再現可能で、
  既知の精度での `hitRate` / `brierScore` の正確な値はユニットテストに固定されています。
- **Amazon Bedrock は呼び出しません。** バックテストは Bedrock・DynamoDB・ネットワークに
  一切触れません。エンジンはそれらに構造的に到達できません（純粋なコードとシードデータしか
  インポートしないため）。
- **「第 k 戦終了時点での予測」。** 完了した各シリーズについて、モデルは毎試合（第 1 戦・
  第 2 戦…）の終了時点で、それまでに行われた試合だけを使って予測し、各予測は実際にシリーズを
  制したチームに対して採点されます。ページは精度設定 `0, 0.25, 0.5, 0.75, 1` について、
  2024 年・2025 年・両シーズン合算の結果を比較します。
  - **注意:** 各シリーズには毎試合の終了時点のスナップショットが含まれ、これにはすでに
    勝敗が決した最終戦も含まれます。その最終スナップショットは予測ではなく確定した結果の
    ため、ヘッドラインの的中率は確定済みの結果を含んでおり、シリーズ途中の予測能力を実際
    より高く見せています。

**指標の定義**（ページ上に表示、EN/JA にローカライズ）:

- **的中率** — 試合ごとのスナップショットのうち、モデルが優勢とみなしたチームが最終的に
  シリーズを制した割合です。高いほど良く、範囲は 0〜1 です。
- **ブライアスコア** — **最終的なシリーズ勝者に対して予測した確率と 1 との平均二乗誤差**です。
  範囲は 0〜1 で、**低いほど良く**、**0 が完璧なスコア**です。
- **キャリブレーション** — **予測を確率のバケットにグループ分けし、各バケットの平均予測確率と、
  そのバケットで実際に観測された勝率を比較**します。よく較正されたモデルでは、予測確率と
  実測勝率が一致します。

### 完了シリーズ: 予測はオフ

現在の予測可能なシーズン内であっても、すでに完了したシリーズ（`status === 'final'`）は、
投機的な予測ではなく**最終結果を表示します**。これは両方のレイヤーで強制されます:

- **バックエンド:** `/prediction` はシリーズを解決し、`final` であれば予測モデルを実行したり
  Bedrock を呼び出したりすることなく `mode: 'results'` を返します。
- **フロントエンド:** 完了シリーズのカードは「勝者を予測」ボタンを描画せず、代わりに
  **「シリーズ詳細を表示」**リンクを表示するため、完了シリーズに対して数値勝率が表示されることは
  ありません。

### 設定可能な予測精度

予測パネルには、モデルの確信度を調整するラベル付きの**精度（accuracy）**スライダーがあります。
`accuracy` は範囲 **`[0, 1]`** のシャープネス制御で、**デフォルトは `0.5`** です:

- `0.5`（デフォルト）は**恒等（identity）**変換で、従来のモデル挙動を変えません。
- **高い**精度（> 0.5）は優勢チーム寄りに予測を鋭くします（より確信的、最大 `0.95` まで）。
- **低い**精度（< 0.5）はコイントス寄りに和らげます（`0` は優勢チームをちょうど `0.5` に収束させます）。

勝率はどの精度値でも**常に `[0.5, 0.95]` の範囲に収まります**（プロパティテストでカバーされる
不変条件）。この制御はエンドツーエンドで配線されており、スライダーは `GET /prediction` に
**`&accuracy=<value>`** クエリパラメーターを付加します（`POST /prediction` のボディでも受け付け
られます）。例: `GET /prediction?seriesId=...&season=2026&accuracy=0.8`。`accuracy` が欠落または
無効な場合はデフォルトにフォールバックし、`400` を発生させることはありません。スライダーを
ドラッグするとデバウンスして予測を再リクエストし、優勢チーム・勝率・ナラティブをライブで更新します。

### 日本語 / 英語の言語切り替え

UI はヘッダーに **JA/EN 言語トグル**を備えています。**日本語がデフォルト**です。選択は
`localStorage`（キー `mlb.lang`）に永続化され、再読み込み時に復元されます。すべてのユーザー向け
文字列がローカライズされています（タイトル / サブタイトル、シーズンラベル、ステータス、ラウンド名、
凡例、順位、精度コントロールを含む予測パネル、試合詳細トグル、詳細ページ）。`TEAMS` マップに存在
しない未知 / プレビューのチーム ID は、生の `Team <id>` ではなく、ローカライズされた
プレースホルダー（EN は `TBD (#<id>)`、JA は `未定 (#<id>)`）で描画されます。

### ローカライズされた AI ナラティブと選択可能な Bedrock モデル

予測ナラティブは**ローカライズ**され、**Bedrock モデルは選択可能**です:

- **ローカライズ（EN / JA）。** ナラティブは、Bedrock のプロンプトと決定論的フォールバックの
  両方について、現在の UI 言語で生成されます。SPA は各 `/prediction` リクエストに UI 言語を
  付加します（`&lang=en|ja`）。`lang` を省略した素の API 呼び出しは英語をデフォルトとします。
  チームのクラブ名は慣例として英語のままで、周囲の文章のみがローカライズされます。
- **モデルセレクター。** 精度スライダーの隣にあるラベル付きセレクターで Bedrock モデルを
  選べます。選択肢は **Amazon Nova** ファミリー — **Nova Micro**・**Nova Lite**（デフォルト）・
  **Nova Pro** — に加え、引き続き利用可能な **Anthropic Claude Haiku** です。（Amazon Titan は
  us-east-1 にテキスト生成モデルがなく埋め込みのみのため、提供しません。）選択は `&model=<id>` と
  して送られ、サーバー側で共有の許可リストに照合されます。未知 / 欠落のモデルはデフォルトに
  フォールバックし、`400` を発生させることはありません。
- **プロバイダー別アダプター + フォールバック。** InvokeModel のリクエスト / レスポンス JSON は
  プロバイダーごとに異なるため、バックエンドは Anthropic の messages ボディと Amazon Nova の
  `messages` + `inferenceConfig` ボディを使い分け、各プロバイダーのレスポンスを解析します。
  Bedrock エラー時（モデルアクセス未有効化を含む）には、要求言語の決定論的テンプレート
  ナラティブを返し、`model` フィールドに `(fallback)` を付加するため、予測は常に HTTP 200 で
  返されます。

> **デプロイ時の注意（Bedrock モデルアクセス）。** IAM はすべての選択可能モデルの InvokeModel
> 呼び出しを認可しますが、各モデルは実行時にテキストを返すためにデプロイアカウント / リージョン
> （us-east-1）で **モデルアクセスが有効化されている**必要があります。モデルアクセスは実行時にのみ
> 顕在化します。選択した Amazon Nova モデルがアクセス未有効化の場合でも、決定論的フォールバックが
> `/prediction` を機能させ続けます（HTTP 200）。ライブ生成のためには、再デプロイ時に Bedrock
> コンソールですべての選択可能モデルのモデルアクセスを確認してください。

### データ整合性の警告

`GET /bracket` のレスポンスは**データ整合性の問題**がないか走査されます。すなわち、完了した
シリーズ、または決着済みの試合が、まだ未確定 / TBD の**プレースホルダーチーム**（`TEAMS` マップに
存在しないチーム ID）を参照しているケースです。プレースホルダーチームは、まだ始まっていない 2026
ブラケットの部分では正常ですが、*完了した*コンテキストは実際に対戦した 2 つの実チームを参照する
べきです。検出結果は HTTP 200 レスポンスに非ブロッキングの `integrityWarnings` 配列として付加され、
サーバー側（Lambda の `console.warn`）にログ出力されます。SPA は非ブロッキングのローカライズ
バナーを表示しつつ、ブラケットを通常どおり描画します。問題のないブラケットではバナーは表示されません。

### 試合詳細トグルと完了シリーズの詳細ページ

- **デフォルトで折りたたまれる試合詳細。** 各シリーズカードは、試合単位のリストをシリーズごとの
  **試合を表示 / 試合を隠す**トグルの背後に隠し、折りたたまれた状態で始まります。これにより
  ブラケットがコンパクトに保たれ、従来の不揃いな（「ガタガタ」の）カード高さと列の整列の主な修正
  となります。
- **完了シリーズの詳細ページ + クライアントサイドルーティング。** SPA はパスベース（history）の
  クライアントサイドルーティング（`react-router-dom`）を使用します。完了シリーズは
  `/season/:season/series/:seriesId` の専用詳細ページにリンクし、試合単位の完全な結果を表示します。
  未知の ID は親切な「シリーズが見つかりません」ページを表示します。パスベースのディープリンクは、
  CloudFront が `403`/`404` レスポンスを `/index.html`（HTTP 200）に書き換えるため、本番でも機能し、
  SPA シェルが読み込まれて要求されたルートを描画します。

### 試合ごとの詳細（ラインスコア・投手・球場・ハイライト）

シリーズ詳細ページでは、各試合が**試合ごとのアコーディオン**を備えています。試合を展開すると、
専用エンドポイントから詳細を**遅延取得**し、次を描画します。

- **イニングごとのラインスコア**（イニングごとの R/H/E＋合計）、
- **勝利 / 敗戦 / セーブ投手**、
- **球場**、
- MLB の content エンドポイントが提供する場合は任意の**リキャップ / ハイライト**リンク。

エンドポイントは **`GET /game?gamePk=NNN`** で、HTTP 200 で `GameDetailResponse` の判別可能な
ユニオンを返します。詳細込みの `{ status: 'ok', ... }`、または上流の MLB 取得に失敗したときの
`{ status: 'unavailable', gamePk }` です。フロントエンドは `status` で分岐するため、**API 失敗時は
すでに表示されている最終スコアにフォールバック**し、エラーにはなりません（`gamePk` は正の整数で
なければならず、そうでない場合は `400`）。

- **MLB Stats API から組み立て。** 純粋でユニットテスト済みのパーサー
  （`backend/src/mlb/gameDetail.ts`）が、`.../game/{gamePk}/linescore` からイニングごと＋合計の
  R/H/E を、`.../v1.1/game/{gamePk}/feed/live` から球場・試合状態・W/L/S の決定を、
  `.../game/{gamePk}/content` から任意のリキャップリンクを取得します（content はベストエフォートで、
  失敗しても呼び出し全体は失敗しません）。
- **試合ごとに DynamoDB にキャッシュ。** `pk = GAME#<gamePk>` でキャッシュファースト（ヒット時は
  取得をスキップ）。TTL は試合状態で選ばれます。**完了**試合は不変なので **1 週間**
  （`GAME_DETAIL_FINAL_TTL_SECONDS = 604800`）、**進行中**試合はライブスコアを新鮮に保つため
  **1 分**（`GAME_DETAIL_LIVE_TTL_SECONDS = 60`）キャッシュします。`unavailable` フォールバックは
  キャッシュしません。
- **モバイル対応のテーブル。** イニングテーブルは横スクロール可能なコンテナに入っているため、狭い画面
  ではテーブル自体が横スクロールし、ページ全体の 375px での横オーバーフロー非発生の保証を崩しません。

`GET /game` ルートは、`TABLE_NAME` だけを持ち **Bedrock へのアクセスを持たない**専用の Node 20
Lambda（`GetGameDetailFn`）が担当し、公開 MLB API と DynamoDB のみに到達します。新しい UI 文字列は
すべて EN / JA 対応です。

### ダークモードとアクセシビリティ

UI はヘッダー（全ページ）に **システム / ライト / ダーク**のテーマ切り替えを備えています。

- **OS の設定に追従。** デフォルトは**システム**で、OS の `prefers-color-scheme` にリアルタイムで
  追従します（OS のテーマを変えるとリロードなしでアプリも切り替わります）。**ライト**または
  **ダーク**を選ぶとその設定が優先されます。選択は `localStorage`（キー **`mlb.theme`**、値は
  `system | light | dark`）に保存され、リロード後も復元されます。アプリの描画前にインラインスクリプト
  がテーマを適用するため、ライトからダークへのちらつきはありません。解決後のテーマは `<html>` の
  `data-theme` として適用され、すべての色（ライト用とダーク用の 2 つのパレットを CSS 変数で定義）が
  まとめて切り替わります。
- **両テーマで WCAG AA のコントラスト。** すべての前景色 / 背景色の組み合わせは、ライト・ダークの
  両パレットで WCAG AA（通常テキスト ≥ 4.5:1、大きいテキストと UI 要素 ≥ 3:1）を満たすように選ばれて
  おり、各チームバッジの略称の文字色はバッジの色から**自動的に算出**されるため、常にディスク上で
  読み取れます。
- **キーボード操作。** ブラケットは**ロービングタブインデックス**方式を採用しています。Tab は一度だけ
  ブラケットに入り、その後は**矢印キー**でシリーズカード間（ラウンドの列内および列をまたいで）を移動し、
  見やすいフォーカスリングが位置を示し、完了シリーズ上で **Enter / Space** を押すと詳細ページが開きます。
  マウス利用者には影響しません。
- **スクリーンリーダー向けラベル。** 各シリーズカードは、2 チーム・シリーズのステータス・スコアを
  読み上げるアクセシブルなラベルを公開するため、視覚に頼らずにブラケットを理解できます。
- **自動アクセシビリティチェック。** Playwright の E2E テスト（`frontend/e2e/a11y.spec.ts`）が
  **[`@axe-core/playwright`](https://www.npmjs.com/package/@axe-core/playwright)**（`@mlb/frontend`
  の devDependency として追加）を使い、ホームのブラケット・完了シリーズの詳細ページ・精度ページを
  **ライトとダークの両テーマ**でスキャンし、**`serious`/`critical` の違反が 0 件**であることを
  アサートします。あわせて、コネクターやロゴを目視確認するためのダークモードのホーム画面の
  スクリーンショットを（gitignore 済みの `frontend/test-results` に）取得します。

### ローカルタイムゾーンの試合開始時刻・今日/明日・カレンダー書き出し

各試合の実際の開始時刻（第一球）をエンドツーエンドで保持し、**閲覧者自身のタイムゾーン**で
表示します。これにより、UTC で日付の遅い試合がローカルで誤った日付に表示されることがなくなります。

- **ローカルタイムゾーンの開始時刻（日本語 / 英語）。** MLB Stats API は各試合の開始時刻を完全な
  ISO UTC 日時で返します。集約処理はそれを追加的・任意の `GameResult.startTime` にそのまま保持します
  （既存の日付のみの `date` フィールドは変更されないため、従来データや同梱シードもそのまま解釈できます）。
  SPA はその時刻を `Intl.DateTimeFormat` で閲覧者のタイムゾーンに変換し、言語ごとに異なる形式
  （`en-US` は 12 時間制、`ja-JP` は 24 時間制、いずれも曜日・月・日を含む）で表示します。開始時刻が
  未定の試合は `timeTbd` フラグが立ち、でたらめな深夜 0 時ではなくローカライズされた
  **時刻未定 / Time TBD** として表示されます。
- **今日・明日の試合 + カウントダウン。** ホームページには「今日・明日の試合」セクションがあり、
  （ローカルのカレンダー日で）今日または明日に行われる各試合を、対戦カード・ローカル開始時刻・
  第一球までのカウントダウンとともに一覧表示します。シーズン外や、残りの試合がすべて時刻未定の
  場合は何も表示しません。
- **カレンダーに追加（.ics）。** 時刻の確定している各試合には **カレンダーに追加 / Add to calendar**
  のダウンロードがあり、標準的な単一イベントの `.ics` ファイルを**完全にブラウザ内で**生成します
  （ネットワーク呼び出しなし、新しいバックエンドエンドポイントなし、インフラ変更なし）。時刻未定の
  試合ではこの操作は表示されません。表示ロジックは、注入されたクロック / タイムゾーン / ロケールを
  受け取る依存のないユニットテスト済みヘルパー（`frontend/src/gameTime.ts`、
  `frontend/src/upcomingGames.ts`、`frontend/src/ics.ts`）にあり、テストで決定的に動作します。

### お気に入りチーム

応援しているチームを登録すると、それだけを追いやすくなります。これはフロントエンドのみの機能で、
バックエンドやインフラの変更はありません。

- **どこからでも登録・保存。** 各チームの行（シリーズカードおよび順位パネル）には**星の切り替え
  ボタン**があります。これはネイティブのボタンで、状態は**形状**で表されます（お気に入りなら塗りつぶし
  の星、そうでなければ輪郭だけの星。色だけに頼りません）。`aria-pressed` とローカライズされた
  `aria-label` を備えます。お気に入り（**複数登録可**）は `localStorage` のキー **`mlb.favorites`** に
  保存され、再読み込み後も復元されます。解析はガードされており、壊れた保存値はアプリを壊すのではなく
  無視されます。
- **色だけに頼らない強調表示。** お気に入りチームを含むシリーズは**色だけに頼らず**強調されます。
  カードヘッダーの**星アイコン**マーカー、独自の**太い破線のボーダー**（グレースケールでも知覚でき、
  ライト・ダーク両テーマで AA コントラスト）、そしてスクリーンリーダーが読み上げる視覚的に隠された
  ラベル（**お気に入りチームのシリーズ / Favorite team's series**）です。
- **敗退の表示。** お気に入りチームがファイナルで敗れると、アクティブな状況から
  ローカライズされた **敗退 / Eliminated** 表示に切り替わります（ブラケットの強調表示とヘッダーの
  ピンの両方で）。
- **ヘッダーのピン。** 「あなたのチーム / Your teams」のピンが、ブラケット内にいる各お気に入りの状況を
  要約します（敗退、優勝、進行中のリード/ビハインド/五分の戦績、または次の試合のローカル開始時刻）。
  お気に入りがない場合や、選択中のシーズンのブラケットにお気に入りがいない場合は何も表示しません。
- **お気に入りのみフィルター。** 「**お気に入りのチームだけ表示 / Show only my teams**」の切り替えで、
  他のシリーズをすべて隠せます。オンにしてもお気に入りのシリーズが現在のブラケットにない場合は、
  空のグリッドではなくローカライズされた分かりやすい空状態を表示します。この切り替えはシーズン
  セレクターと共存します（シーズンを切り替えても状態は維持されます）。
- **EN / JA。** お気に入り関連の文字列はすべてローカライズされています。ロジックは、純粋でガードされた
  ストア（`frontend/src/favorites.ts`）、`FavoritesContext`/`useFavorites()` のグルー、純粋な
  ブラケットヘルパー（`frontend/src/bracketLayout.ts` の
  `findTeamSeries`/`isTeamEliminated`/`favoriteSummary`）、`FavoriteToggle`・`FavoritesPin`
  コンポーネント、そしてブラケットの強調表示/フィルターにあります。

### シリーズの流れの可視化

シリーズの流れを一目で把握できます。これは**フロントエンドのみ**の機能で、バックエンドや
インフラの変更はありません。確率オーバーレイは**純粋な共有 `predict()`** を再利用しており、
Bedrock やライブ MLB 呼び出しは一切行いません。

- **詳細ページのチャート。** 試合のあるシリーズを開くと、コンパクトなインライン SVG チャートが
  表示されます。**試合ごとの得点差の棒グラフ**と**シリーズ累計勝利数の推移グラフ**で、棒と線は
  各チームのブランドカラーで描画されます。
- **過去 / シードシーズンでは予測オーバーレイなしで動作。** チャートは同梱の **2024・2025**
  シードシーズン（完全オフライン）でも**予測オーバーレイなしで**描画されます。**予測可能な今シーズン**
  （かつ試合のあるシリーズ）に限り、**予測勝利確率の推移**チャートが追加されます。
- **アクセシブルで色だけに依存しない。** 各チャートは `role="img"` とアクセシブルな名前を持つ
  SVG で、同じ数値をテキストで伝える本物の**データ表**（**「データ表を表示/隠す」**トグルで折りたたみ）
  と対になっています。**勝者はテキスト**（`{team} が勝利` / `引き分け` / `進行中`）で示され、色だけに
  依存しません。軸・グリッド線・ラベルはテーマ変数を使うため、**ダークモード**でも読みやすさを保ちます。
- **ブラケットカードのスパークライン。** 試合のある各ブラケットカードに、控えめでテーマ対応の
  **得点差スパークライン**（ローカライズされた `aria-label` を持つ単一の `role="img"` 要素で、
  フォーカス可能な子要素なし）が表示されます。タブ停止を増やさず、キーボードモデルやお気に入りの
  強調表示を回帰させず、375px のモバイル幅でもはみ出しません。
- **EN / JA。** すべての文字列がローカライズされています（既定は日本語）。ロジックは純粋でテスト済みの
  ヘルパー（`frontend/src/seriesCharts.ts`。試合ごとの切り詰めは共有の `seriesProbTrend` に委譲）と、
  `SeriesFlowCharts`・`ScoreDiffSparkline` コンポーネントにあります。

## Amazon Bedrock の利用

勝率は `backend/src/predict/` 内の透明なヒューリスティックで計算されます（現在のシリーズ進行度を
レギュラーシーズン勝率とブレンドし、`[0.5, 0.95]` にクランプ）。次に **Bedrock**
（`BEDROCK_MODEL_ID`、デフォルトは `us.amazon.nova-lite-v1:0`、クロスリージョン推論プロファイル）が、
要求言語（EN / JA）で簡潔な 2〜3 文のナラティブとして選定理由を説明します。モデルはリクエストごとに
共有の許可リストから選択可能です — **Amazon Nova** ファミリー（`us.amazon.nova-micro|lite|pro-v1:0`、
デフォルトは Nova Lite）に加えて **Anthropic Claude** Haiku 推論プロファイル — そして小さな
プロバイダー別アダプターが各プロバイダーのリクエスト / レスポンス JSON を整形します。Bedrock が
エラーになった場合（リージョンでモデルアクセスが有効化されていない場合を含む）、エンドポイントは
同じ言語の決定論的なテンプレートナラティブへ適切に劣化するため、予測は常に返されます。デフォルト
モデルはデプロイ時に `cdk deploy --context bedrockModelId=<id>` で上書きできます。

## 画像アセット

UI は `frontend/src/assets/` 配下の**実際のコミット済み SVG 画像アセット**（絵文字ではありません）
を使用します — ブランドロゴ、野球 / ダイヤモンドのヒーロー、リーグ / ワールドシリーズのマーク、
さらにチームごとの色で駆動される生成済みのチームカラー SVG バッジです。SVG は「実際の画像アセット」
要件を満たしつつ、リポジトリを軽量に保ちます。

## 前提条件

- **Node.js 20+**（ローカルのツールチェーンは Node 22 かもしれませんが、コードは Node 20 の Lambda
  ランタイムを対象とします）。
- シェル / セッションで有効な認証情報を持つ **AWS アカウント**（プロファイル、SSO、または環境変数）。
- 選択可能なモデルに対する **Amazon Bedrock のモデルアクセスがデプロイリージョン（us-east-1）で
  許可されていること**。デフォルトは **Amazon Nova Lite**（`us.amazon.nova-lite-v1:0`、クロス
  リージョン推論プロファイル）で、その他の選択肢は Nova Micro・Nova Pro・Anthropic Claude Haiku
  プロファイル（`us.anthropic.claude-haiku-4-5-20251001-v1:0`）です。デプロイ前に、使用する予定の
  モデルについて Bedrock コンソールでモデルアクセスを有効化してください — **モデルアクセスは実行時
  にのみ顕在化し**、アクセス未有効化のモデルは決定論的ナラティブにフォールバックします。デフォルトが
  推論プロファイル ID（プレフィックス `us.`）なのは、これら現行世代モデルが推論プロファイル経由の
  オンデマンドで呼び出されるためです。Lambda の IAM ポリシーは、推論プロファイルと、それがルーティング
  し得る US リージョン全体の基盤モデルに対して `bedrock:InvokeModel` を付与し、Amazon Nova モデルと
  Claude プロファイルの両方をカバーします。デフォルトモデルは
  `cdk deploy --context bedrockModelId=<id>` で上書きできます。
- CDK は **esbuild** で Lambda をバンドルします（Docker 不要）。

> **注:** デプロイ前に AWS 認証情報が有効で**かつ**、生成に使う各選択可能モデルについて Bedrock の
> モデルアクセスがリージョン（us-east-1）で許可されている必要があります。モデルアクセスは実行時に
> のみ顕在化し、それ以外は決定論的フォールバックがエンドポイントを機能させ続けます。リポジトリの
> ビルド自体はライブの AWS / Bedrock 呼び出しを行いません。

## ワンコマンドデプロイ

リポジトリルートから、有効な AWS 認証情報の下で:

```bash
npm install && npm run build && npm run deploy
```

- `npm install` — すべてのワークスペースをインストールします。
- `npm run build` — 依存順にビルドします: `shared → backend → frontend → infra`。CDK が synth 時に
  `frontend/dist` を S3 ウェブサイトソースとしてパッケージするため、フロントエンドはデプロイ**前に**
  ビルドされる必要があります。
- `npm run deploy` — 順序付きビルドを再実行してから、`@mlb/infra` ワークスペースの `cdk deploy` を
  実行します。

### 初回セットアップ（CDK ブートストラップ）

対象アカウント / リージョンへの初回 CDK デプロイの場合、一度だけブートストラップします:

```bash
cd infra
npx cdk bootstrap
npx cdk deploy
```

（リポジトリルートからは `npm run bootstrap` のあと `npm run deploy` も実行できます。）

デプロイ後、スタックは出力を表示します:

- **ApiUrl** — HTTP API のベース URL。
- **DistributionDomainName** — ブラウザーで開く CloudFront ドメイン。
- **BucketName** — SPA をホストする S3 バケット。
- **TableName** — DynamoDB キャッシュテーブル。

### SPA が API を見つける仕組み（再ビルド不要）

同じ静的バンドルは**デプロイ時**に任意のデプロイ済み API へ向けられます。CDK がバケットルートに
`window.__API_BASE_URL__ = "<ApiUrl>";` を含む `/config.js` を書き込み、アプリバンドルより前に
`index.html` が読み込みます。実行時、SPA は `window.__API_BASE_URL__` を読み取り、ビルド時の
`VITE_API_BASE_URL`、最後にローカルのデフォルトへフォールバックします。

### デプロイせずに検証

AWS に触れずに CloudFormation テンプレートを検証するには:

```bash
npm run build        # SPA アセット用に frontend/dist が存在することを保証
npm run synth        # cdk synth -> infra/cdk.out（AWS 呼び出しなし）
```

## ローカル開発

```bash
npm install
npm run dev -w frontend     # Vite 開発サーバー（http://localhost:5173）
```

デフォルトでフロントエンドは API に `http://localhost:3000` を使用します。データのオプション:

- **オフライン / シードデータ:** ブラケットリクエストが失敗すると、SPA は自動的に同梱の
  `@mlb/shared` シード（2024 と 2025）へフォールバックするため、完了シーズンのブラケットは
  バックエンドなしで描画されます。
- **デプロイ済み API を指す:** `VITE_API_BASE_URL=<ApiUrl> npm run build -w frontend` でビルドするか、
  （デプロイ済みサイトのように）`/config.js` 経由で `window.__API_BASE_URL__` を設定します。

モノレポ全体でテストスイートと型チェックを実行:

```bash
npm test          # ワークスペース全体の Vitest（AWS SDK + MLB API はモック）
npm run typecheck # 全ワークスペースで厳格な TypeScript
```

## ステアリングファイルと Kiro University レッスンの対応

`.kiro/steering/` 配下のステアリングセットがビルドを駆動し、試験の必須レッスンを実証します:

| ステアリングファイル          | 何を駆動するか                                              | Kiro University レッスンテーマ |
| ----------------------------- | ----------------------------------------------------------- | ---------------------------- |
| `kiro-university.md`          | チャレンジのルール・採点・ビルドがレッスンにどう対応するか  | スペック / ステアリング駆動開発 |
| `product.md`                  | プロダクトのビジョン・機能・制約・非目標                    | 要件 → スペック品質           |
| `tech.md`                     | 承認済みの AWS アーキテクチャと TypeScript ツールチェーン   | Infrastructure as Code（CDK）+ AWS 統合 |
| `structure.md`                | モノレポ構成と規約                                          | プロジェクト構造 / 保守性     |

具体的には、各レッスンは次のように実証されます:

- **スペック / ステアリング駆動開発** — このステアリングセットと、`.agents/tasks/` 配下の
  個別に計画された機能。
- **Amazon Bedrock 統合** — 勝敗予測ナラティブは、おもちゃではない本物の AI 統合です（プロバイダー別
  アダプター経由で選択可能な Amazon Nova / Claude モデル、EN/JA ローカライズ、決定論的フォールバック
  付き）。
- **Infrastructure as Code** — AWS CDK がワンコマンドデプロイのためにスタック全体をプロビジョニング
  します。
- **テスト** — Vitest のユニットテストが、予測ロジックと MLB 集約を AWS と MLB API をモックして
  カバーします（CI でライブ呼び出しなし）。
- **ドキュメント** — この README がワンコマンドデプロイとローカル開発をカバーします。
