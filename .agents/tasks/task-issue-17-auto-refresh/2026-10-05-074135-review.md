# Background auto-refresh for an in-progress bracket (v1)

Issue #17 asks the bracket to keep itself current while a series is live: poll only when a series is in progress, show a localized "last updated" line plus a manual refresh button, pause when the tab is hidden, and never flicker or lose the selected series on refresh. The change is frontend-only, split into a pure relative-time formatter (`relativeTime.ts`), a visibility-aware polling hook (`useAutoRefresh.ts`), and the wiring/rendering in `HomePage.tsx`, with EN/JA strings and a 60s named constant tied to the ~15min backend cache TTL. The three acceptance criteria (no polling for results-only seasons, flicker-free refresh preserving scroll and selection, failed refresh keeps prior data with an unobtrusive error) are all satisfied in the code, and the stale-season race is additionally guarded. The unit coverage of the hook and page behavior is strong and would fail if the behavior were reverted.

Watch for: the results-only e2e test waits 3s against a 60s interval, so it would pass even if polling were wrongly enabled — the assertion is effectively vacuous for its stated purpose (confirmed). No end-to-end test exercises actual interval-driven auto-polling; that path is only covered by the fake-timer unit test (confirmed, acceptable).

**Verdict**: APPROVED

## High-level view

Polling is gated by `pollingEnabled = isPredictable(season) && status==='ready' && series.some(in_progress)`, passed as the hook's `enabled`. Results-only seasons and predictable-but-quiet seasons never arm the interval, which is criterion 1. The gate is derived from live bracket state, so it re-evaluates when a series flips to or from `in_progress`.

The flicker-free guarantee comes from the background `refresh()` never writing `status: 'loading'` and never clearing `selectedSeriesId`. The bracket stays mounted across a refresh, so scroll and the selected series survive (criterion 2). A `seasonRef` captures the requested season and every branch of the refresh bails if the user has since switched seasons, so a late in-flight refresh cannot clobber the newly selected season's bracket (criterion 8, beyond the issue's three).

Failure handling keeps the previously loaded bracket and sets a localized inline `refreshError` rendered as a subtle `.app__notice--refresh`, distinct from the full-screen `.app__status--error` first-load path; the next success clears it (criterion 3).

The relative-time formatter is pure and clamps invalid or future (clock-skew) timestamps to "now"/"今", so a backend `updatedAt` slightly ahead of the client never renders "in N minutes". i18n key parity is enforced at compile time by the `Record<Lang, Record<MessageKey, string>>` typing rather than a runtime test.

The weak spot is e2e: the negative (results-only) test's timing window is far shorter than the poll interval, so it does not actually prove polling is off, and no e2e proves polling is on. The unit layer covers both, so this is a test-strength gap, not a behavioral defect.

### Polling gate and the in-progress predicate

Because `pollingEnabled` reads the loaded bracket, the interval arms and disarms as series transition, not just at mount — a season that goes live mid-session starts polling, one whose last series goes final stops. The `enabled:false` path installs no interval and no `visibilitychange` listener.

A render asymmetry worth noting (intended): the manual refresh bar renders under `bracketStarted`, a broader condition than `hasInProgressSeries`. So a predictable season that has started but has no in-progress series shows the manual Refresh button yet does not auto-poll — manual refresh is available once there is content, auto-polling is reserved for live series.

### Flicker-free refresh and the stale-season guard

```
refresh():
  requestedSeason = seasonRef.current
  getBracket(requestedSeason)
    .then  -> if seasonRef.current !== requestedSeason: return   // stale, drop
              setState(ready, newBracket); clear refreshError; bump now
    .catch -> if stale: return; setRefreshError(t('refresh.error'))
    .finally-> if stale: return; setIsRefreshing(false)
```

Unlike the first-load effect, the background path never sets `status: 'loading'` and never touches `selectedSeriesId`, so the bracket region stays mounted and scroll position and the selected series are preserved (criterion 2). The HomePage test asserts the bracket region stays in the document during and after a manual refresh and that the "selected for prediction" marker survives the second fetch — it would fail if `refresh()` reintroduced the loading swap or reset the selection.

The stale guard is complete: all three continuations compare against the `requestedSeason` captured at call time, so a refresh that resolves after the user navigated away is dropped on every branch including `finally`, and `isRefreshing` for the stale request never toggles the new season's state. The new season's first-load effect independently resets `isRefreshing`/`refreshError`, so there is no stuck-spinner path. This covers criterion 8 — the real race the issue did not call out.

### Failed refresh stays unobtrusive

On rejection the previous bracket is left untouched and `refreshError` renders as `.app__notice--refresh` with `role="status"` — not the `role="alert"` `.app__status--error` first-load path. The HomePage test asserts prior data stays mounted, `queryByRole('alert')` is null, and a subsequent success clears the notice, so it distinguishes the two error surfaces rather than merely matching a string.

### Visibility pause/resume

On becoming visible the hook fires an immediate `onRefresh()` before restarting, so a tab hidden across several intervals shows fresh data on return instead of waiting up to a full period. The unit test drives `visibilitychange` with a mocked `document.hidden` and asserts no ticks while hidden, exactly one immediate call on resume, then resumed ticks — it would fail if the pause, the immediate refetch, or the resume were dropped. `onRefresh` is held in a ref, and `HomePage`'s `refresh` is a `useCallback` depending only on `t`, so its identity is stable across refreshes and the running timer is never reset.

### Test strength gap in e2e

The positive e2e spec drives the manual button and never waits for the interval, so interval-driven auto-polling is unverified end-to-end — only the fake-timer unit test covers it. The negative spec is the real gap: it switches to results-only 2024 and waits 3s to assert no extra `/bracket` fetch, but with a 60s interval no tick could fire in 3s even if polling were erroneously enabled, so the assertion cannot fail for the reason it claims to test. The guarantee for criterion 1 rests entirely on `useAutoRefresh.test.tsx`'s `enabled:false` case. A test-only shorter interval (env or Playwright-injected) would let the negative e2e actually prove the gate.
