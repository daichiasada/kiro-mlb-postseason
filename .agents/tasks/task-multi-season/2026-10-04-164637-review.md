# Year-aware multi-season support with results-only gating and a 2026 prediction contract (v1)

The site now treats 2026 as "now": a single `CURRENT_YEAR` constant in `@mlb/shared` drives a season classifier (`seasonMode`/`isResultsOnly`/`isPredictable`), seasons before it (2024, 2025) are results-only, and the current year keeps the prediction feature. The backend derives its default season from that constant and returns a typed `PredictionResponse` discriminated union (always HTTP 200) with `prediction` / `results` / `upcoming` modes so results-only seasons short-circuit before the predict model or Bedrock are ever touched. A real aggregated 2025 seed (Dodgers over Blue Jays, 4-3) was added so the offline fallback serves both past seasons, and the SPA gained a season selector plus a results-only treatment and a 2026 empty-state message. The gating is genuinely centralized in the shared helper rather than scattered literals, and the new tests exercise the real code paths (they assert the Bedrock invoker is / isn't called per mode) rather than asserting statics.

Watch for: the backend `upcoming` short-circuit and the frontend empty-state both key on `status === 'scheduled'`, but a real 2026 schedule records "Preview" games, which the aggregator turns into `in_progress` 0-0 series — so the documented graceful empty/upcoming path is not what the live 2026 shape actually hits (confirmed). The empty-state is only tested with synthetic `scheduled` brackets, so this gap is invisible to the suite (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The season model is clean: `CURRENT_YEAR` is the single source of truth, `seasonMode` classifies anything other than the current year as results-only, and both backend (`http.ts`) and frontend (`config.ts`) default to it by import rather than by literal. The one semantic wrinkle is that future seasons also classify as `results` while `getSeedBracket` only serves 2024/2025 — benign today but worth knowing.

The `/prediction` contract is a discriminated union over three modes, always 200. Results-only seasons return `mode:'results'` before any store, predict, or Bedrock call — a clean fail-closed boundary that keeps completed seasons from spending model budget. The predictable path returns `mode:'prediction'`; unresolvable or `scheduled` series return `mode:'upcoming'`.

The gap is in what "not started" means. The aggregator records every game it sees, including `Preview` games, so a 2026 series that only has preview games becomes `in_progress` with 0-0, not `scheduled`. Both the backend `upcoming` guard (`!series || status === 'scheduled'`) and the frontend `hasStartedContent` guard treat `scheduled`-with-no-games as the only not-started shape. Against the real 2026 schedule described in the task context (13 Final + 37 Preview games), preview-only series render as live in-progress cards and are predictable with placeholder team ids — the opposite of the documented "The 2026 postseason has not started yet" behavior.

The 2025 seed is real aggregated data with a deterministic `updatedAt`, every referenced team id is in the extended `TEAMS` map, and the World Series resolves to the Dodgers at 4-3. The specs, README, and steering were updated to match the implementation. Test coverage is strong on the modeled paths but has a blind spot exactly where the preview-game gap lives: the empty-state is only exercised with hand-built `scheduled` brackets, never with the preview-game shape the live API returns.

<summary>Details</summary>

### Season classifier: future seasons have no seed

The classifier maps everything that isn't `CURRENT_YEAR` to `'results'`, including future years, while `getSeedBracket` only knows 2024 and 2025. A hypothetical 2027 request would be classified results-only yet have no seed, so if its live fetch failed, `getBracket` rethrows and the handler 500s rather than degrading to a results view. Not reachable from the UI today; flagging because the "results-only" label implies a results view exists.

### Prediction contract short-circuits before predict/Bedrock

The results-only branch returns before `getBracket`, `predict`, or Bedrock:

```ts
if (isResultsOnly(season)) {
  return { mode: 'results', seriesId, season, message: `The ${season} postseason is complete; ...` };
}
```

Verified by the service test asserting `store.getCachedBracket`, `fetchSchedule`, and the Bedrock invoke are all untouched for 2024/2025. A completed season can never spend model budget or hit the network — fail-closed on a feature that should be hidden on past seasons.

### The "not started" definition diverges from the live 2026 shape

The aggregator appends every raw game to the accumulator unconditionally; it never filters on `status.abstractGameState`. Status is then derived purely from win counts and game presence:

```ts
if (highWins >= clinch || lowWins >= clinch) status = 'final';
else if (acc.games.length === 0) status = 'scheduled';
else status = 'in_progress';
```

So a series whose only games are `Preview` entries (score `null`, `isWinner` `null`) has `games.length > 0` and zero wins, yielding `in_progress` at 0-0. Both guards that implement the "upcoming/empty" behavior only recognize the `scheduled` shape:

- Backend: `if (!series || series.status === 'scheduled')` → `mode:'upcoming'`.
- Frontend: `hasStartedContent` returns true when any series is `status !== 'scheduled' || games.length > 0`.

The task context describes the real 2026 snapshot as 13 Final + 37 scheduled "Preview" games with placeholder teams. Under that input every preview-only series is `in_progress`, so `hasStartedContent` is true and the SPA renders the bracket grid of placeholder cards instead of "The 2026 postseason has not started yet." On the backend, a client that requests one of those preview-only series gets `mode:'prediction'` — `predict()` runs on a 0-0 series and returns the high seed at ~0.5 via the home-field edge, with a Bedrock narrative built on placeholder team ids. The documented upcoming path is bypassed exactly in the scenario it was written for. The findings in FEAT-002 acknowledge this ("a preview-only series aggregates to status 'in_progress'"), but the acceptance criterion ("no in-progress series → upcoming/empty message") is not met for the real data shape, only for a bracket that is literally empty or whose series were hand-set to `scheduled`.

The fix is a definition of "started" that excludes decided-nothing series — e.g. treat a series with no game that has a non-null winner as not-started — applied in both the service guard and `hasStartedContent`, or have the aggregator classify a games-but-no-results series as `scheduled`. Either way the two guards must agree with the aggregator's output on real data.

### 2025 seed is internally consistent

`postseason-2025.json` references team ids (111/112/113/136/141 among them) that are all present in the extended `TEAMS` map, so the frontend never falls back to `Team <id>` for past seasons. The seed test asserts the champion and 4-3 score rather than snapshotting the file, so it would catch a regenerated-but-wrong seed.

### Test coverage: strong on modeled paths, blind on the preview shape

The service tests exercise real `getPrediction`/`getBracket`/`aggregateBracket` and would fail if the behavior were reverted: results-only asserts no store/fetch/Bedrock contact; the predictable path asserts a favorite in-series with probability in [0.5, 0.95] and exactly one Bedrock invoke; the placeholder-team test feeds unknown ids (9001-9004) mixed with a real Final game and asserts aggregation doesn't throw and no win exceeds clinch. The frontend tests drive the real selector and assert the prediction affordance appears for 2026 and is absent for 2024, with the bracket still rendering.

Not tested: the actual live 2026 shape. The "upcoming" and empty-state cases are built from synthetic brackets whose series are explicitly `status: 'scheduled'` with no games (`bracket2026Upcoming`, the scheduled-series service test). Nothing feeds `Preview` games through `aggregateBracket` and asserts the resulting bracket drives the upcoming/empty treatment — which is precisely why the preview-game gap passes CI green. A test that aggregates preview-only games and then asserts `mode:'upcoming'` (service) and the "has not started yet" message (App) would both document the intended contract and fail against the current code.

### Docs match the implementation

Spot-checking the FEAT-004 claims against the code: the specs and README describe `CURRENT_YEAR`/`SELECTABLE_SEASONS`, the results-only vs predictable rule, the `PredictionResponse` contract with its three modes at HTTP 200, the placeholder-team tolerance, and the seed fallback now covering 2024+2025 — all of which are present in the shipped code. The spec-driven-development lesson is satisfied, with the caveat that the specs describe the upcoming/empty behavior as if it triggers on the real 2026 data, which (per the gap above) it does not.
