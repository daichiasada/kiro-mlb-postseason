# Preview-only series now reach the 2026 upcoming/empty path (v2)

The v1 blocking issue — a not-yet-started 2026 series rendering as a live 0-0 `in_progress` card and being predicted on placeholder ids — is resolved by changing what "started" means. `aggregateBracket` now keys `scheduled` on "no decided game" rather than "no games at all": a series whose only games are live-API "Preview" entries (null score, null `isWinner`) decides nothing and classifies as `scheduled`. The backend `upcoming` guard gained a `hasStartedSeries()` helper and the frontend `hasStartedContent` gained `hasSeriesStarted()`, both keyed on a decided game / recorded win, so all three layers agree on the real preview shape. New tests feed the genuine preview shape through the aggregate, service, and App layers; specs were updated to state the "no decided game" definition truthfully.

Watch for: nothing blocking. The frontend `hasSeriesStarted` ignores `series.status` entirely and keys purely on wins/decided games, which is more robust than the backend's `status === 'scheduled'` short-circuit but means the two guards use slightly different predicates to reach the same answer (confirmed, benign). Issue 3 (seedless future results-only season) remains documented-not-guarded, which is correct given the fixed selector (confirmed).

**Verdict**: APPROVED

## High-level view

The status semantics are now consistent end to end. The aggregator derives `final` from the clinch count, `scheduled` when zero games have a decided winner (covering both an empty series and a preview-only series), and `in_progress` otherwise. A genuinely-started series — any series with at least one game that has a real winner — is unchanged: it still reaches `in_progress` or `final` and stays predictable. The semantics change lives at the one place status is computed, and the two downstream guards defend the same condition rather than re-deriving status, so there is a single source of truth for "started".

The three "not started" predicates agree on the real 2026 shape. Aggregator: `decidedGames === 0 → scheduled`. Backend `hasStartedSeries`: false when `scheduled`, or when no win is recorded and no game has a real winner. Frontend `hasSeriesStarted`: true only when a win is recorded or a game has a real winner. The backend adds a `status === 'scheduled'` fast-path the frontend omits, but because the aggregator already sets `scheduled` exactly when no game is decided, both guards return the same answer for every bracket the aggregator can produce.

The new tests exercise the actual preview shape, not a synthetic `scheduled`-with-no-games stand-in. The aggregate suite drives Preview games (null winners) and asserts `scheduled`, and a mixed Final+Preview series and asserts `in_progress`. The service suite feeds a real preview-only 2026 schedule through `getBracket`/`aggregateBracket`/`getPrediction` and asserts `scheduled` then `mode:'upcoming'`. The App test uses a bracket carrying preview games (`games.length > 0`) and asserts the "has not started yet" message — the exact shape that slipped through the old `games.length > 0` check, so it fails against the reverted frontend.

Issue 3 is handled by documentation rather than a guard: `getBracket`'s seedless rethrow now carries a comment noting that `SELECTABLE_SEASONS = [2026, 2025, 2024]` all have a seed or are live, so a seedless future results-only season is unreachable from the UI. Acceptable given the fixed selector. Specs (requirements.md, design.md, tasks.md) were updated to describe the decided-game definition, so they no longer claim the upcoming path triggers on a shape the code wouldn't actually hit.

### Status semantics moved to "no decided game"

The aggregator still records every raw game unconditionally, but status derivation changed. It counts `decidedGames` as games where either side has `isWinner === true`, and classifies:

```ts
if (highWins >= clinch || lowWins >= clinch) status = 'final';
else if (decidedGames === 0) status = 'scheduled';
else status = 'in_progress';
```

The only behavioral change versus v1 is the middle branch: previously `acc.games.length === 0 → scheduled`, now `decidedGames === 0 → scheduled`. A preview-only series (games present, all winners null) was `in_progress` 0-0 under v1 and is `scheduled` now. A series with no games at all is still `scheduled` (zero decided games). A series with at least one decided game is still `in_progress` or `final` — the existing "marks an unfinished series as in_progress" test uses a decided game and still asserts `in_progress`, confirming genuinely-started series are untouched. The `final` branch is independent of the change.

### Three guards, one definition

The backend defends the same condition at the prediction boundary:

```ts
function hasStartedSeries(series: Series): boolean {
  if (series.status === 'scheduled') return false;
  if (series.high.wins > 0 || series.low.wins > 0) return true;
  return series.games.some((g) => g.away.isWinner === true || g.home.isWinner === true);
}
```

`getPrediction` returns `mode:'upcoming'` when `!series || !hasStartedSeries(series)`, so a preview-only series — now `scheduled` out of the aggregator — short-circuits before `predict()` or Bedrock, which was the whole point: no prediction on placeholder team ids.

The frontend `hasSeriesStarted` drops the `scheduled` fast-path and keys purely on wins/decided games. For any aggregator output the two predicates coincide, because the aggregator sets `scheduled` exactly when no game is decided and no win exists. The divergence is only reachable by a hand-built bracket whose `status` contradicts its games, which the aggregator never emits; the App tests build such fixtures (`status:'scheduled'` with preview games) precisely to prove the frontend ignores the field and keys on the games, which is the stronger guarantee.

### Tests would fail if the fix were reverted

The aggregate test "classifies a preview-only series ... as scheduled" asserts `games.length === 2` and `status === 'scheduled'` simultaneously — impossible under v1's `games.length === 0` rule, so it fails on revert. The companion mixed Final+Preview test asserts `in_progress`, pinning the boundary.

The service test "returns mode:upcoming for a preview-only series" is the end-to-end proof: it mocks `fetchSchedule` with `previewOnly2026Games` (all Preview, null winners), lets the real `getBracket`/`aggregateBracket` run, resolves the aggregated Wild Card id, and asserts `mode:'upcoming'`. Under v1 that series aggregates to `in_progress` and the response is `mode:'prediction'`, so this fails on revert.

The App test "shows the upcoming message for the real 2026 preview-game shape" uses `bracket2026Preview` — a series with `games.length > 0` carrying preview games. The old `hasStartedContent` (`status !== 'scheduled' || games.length > 0`) returns true on `games.length > 0` and renders the grid; the test asserts the "has not started yet" message, so it fails against the reverted frontend. This is the synthetic-vs-real gap v1 flagged, now closed.

### Issue 3: seedless future season documented, not guarded

`getBracket`'s rethrow on a missing seed now carries a comment: reachable seasons (`SELECTABLE_SEASONS = [2026, 2025, 2024]`) all have a seed (2024/2025) or are live (2026), so a seedless future results-only season (e.g. 2027) cannot be requested from the UI; if one is ever added it must ship a seed. The v1 review rated this `possible` and non-blocking; documenting the invariant at the throw site is a proportionate response, and no new code path makes 2027 reachable.
