# Regular-season win pct wired into predictions (v1)

Until now `BracketService.getPrediction` passed a hardcoded `this.winPct` (effectively `{}`) into the pure `predict()` model, so the regular-season strength signal was neutral 0.5 for every team and only series progress moved the needle. This change fetches the real regular-season standings from the MLB Stats API (`?leagueId=103,104&season=YYYY`), aggregates them with a pure `winPctFromStandings` function, caches the per-team map in DynamoDB under `STANDINGS#<season>`, resolves it through a layered `resolveWinPct` (injected map → cache hit → live fetch+write-back → neutral `{}` on any failure), and surfaces the per-team win pct used on an additive optional `Prediction.metrics` field that the frontend renders as a localized EN/JA "Prediction basis" block. The fallback never throws, so a standings outage degrades to the prior progress-only behavior rather than failing the request.

Watch for: the live `fetchStandings` wrapper's non-200 / network error path has no direct unit test — its `MlbApiError` throw is only exercised transitively via the service-level reject test (confidence: confirmed, low severity, consistent with the pre-existing untested `fetchPostseasonSchedule`). No functional blocking issues found; all three acceptance criteria are met and the tests are non-vacuous.

**Verdict**: APPROVED

## High-level view

The resolution order in `resolveWinPct` is the heart of the change. An injected non-empty map wins first (preserving the existing test seam), then the DynamoDB standings cache, then a live fetch that aggregates and writes back; any failure in the cache/fetch path collapses to `{}`, which `predict()` already interprets as neutral 0.5 per team. The whole path is wrapped so it never throws, which is exactly acceptance criterion 1 — a prediction is always returned.

The aggregation is isolated in a pure, side-effect-free `winPctFromStandings` that parses the API's two win-pct notations (`.580` and `0.580`) via `Number()`, rejects non-finite and out-of-range values, skips entries with no team id, and returns `{}` for empty/early-season payloads. Because it takes a plain JSON object and touches no network or AWS, it is unit-tested directly with fixtures (criterion 2).

The response contract gains an additive optional `metrics: { favorite, underdog }`, each `{ teamId, winPct: number | null }`, where `null` records that the neutral fallback was used for that team. Older producers omit it and the `results`/`upcoming` variants are untouched, so the change is backward compatible. The frontend renders this behind a presence guard as a localized "Prediction basis" block, showing each team's win pct as a percentage or a localized "Not available" for `null` (criterion 3).

The standings cache reuses the existing single-`pk` bracket table with a `STANDINGS#<season>` key and the same ~15 min TTL, so no infra schema change was needed. Docs (design, requirements, tasks, both READMEs) were updated to describe the standings-driven signal and explicitly state that no Pythagorean/last-10 signal is implemented, matching the code.

### resolveWinPct resolution order and the never-throw guarantee

`resolveWinPct(season)` is the single point where the strength signal is resolved, and its ordering is deliberate: a non-empty injected `this.winPct` returns immediately (keeping every pre-existing `winPct`-injection test valid without touching the store), otherwise the cache is consulted, otherwise a live fetch is aggregated and written back. The entire cache/fetch block sits inside a `try` whose `catch` returns `{}` — so a network failure, a non-200 from `fetchStandings`, or a malformed payload all degrade to the neutral map that `predict()` treats as 0.5 per team. This is acceptance criterion 1, and the service test `falls back to neutral (null metrics) and still predicts when fetchStandings throws` pins it: on a rejected fetch the response is still `mode: 'prediction'`, the favorite is still computed from series progress, and `putCachedStandings` is asserted NOT to have been called (no write-back of a bogus map). The cache-hit test asserts `fetchStandings` is never called and no write-back occurs, and the happy-path test asserts a cache miss triggers exactly one fetch and one write-back. Reverting the wiring (passing `this.winPct` back into `predict`) would break the metrics assertions in all three tests, so they are not vacuous.

One behavioral note on the injected guard: `Object.keys(this.winPct).length > 0` means an injected empty object is indistinguishable from "nothing injected" and falls through to the cache/fetch path. That matches the documented intent (the default `this.winPct` is `{}`), but it means there is no injection path that forces a neutral map while skipping the fetch.

### Pure aggregation of the standings payload

`winPctFromStandings` is the criterion-2 pure function. It walks `records[].teamRecords[]`, and for each entry parses `winningPercentage` with `Number()`, which handles both the leading-dot `.580` and leading-zero `0.580` notations the MLB API returns — the test `parses both '.580' and '0.580' notations to the same number` locks this. Guards reject a missing/non-numeric `team.id`, an empty/absent `winningPercentage`, and any parsed value that is non-finite or outside `[0, 1]`; the `skips entries with a missing team id or unparseable pct` test exercises each of those branches and confirms a valid sibling entry still survives. An empty, absent, or early-season (`teamRecords: []`) response yields `{}`, so early-season callers get a neutral map rather than a crash. The function touches no network or AWS, which is what lets the test suite drive it entirely from fixture JSON with no live calls.

The out-of-range rejection (`pct > 1` → skipped, not clamped) is worth calling out as a design choice: a corrupt `1.5` is dropped so the team silently falls back to neutral 0.5 in the model, rather than being clamped to a misleading 1.0. That is the safer failure mode here.

### Additive metrics contract and backward compatibility

`Prediction.metrics` is optional (`metrics?: PredictionMetrics`), and `PredictionMetrics` splits into `favorite`/`underdog` `TeamMetric`s carrying `winPct: number | null`. `null` is the explicit encoding of "neutral fallback was used for this team," which is how the service represents a cache/fetch failure in the response — the reject test asserts both roles come back `winPct: null`. The service derives the underdog as the series team that is not the favorite, and builds both metrics with `teamMetric(winPct, id)`, which returns `winPct[id] ?? null`; so a team present in the map reports its real pct and a team absent (partial standings) reports `null`. Because the field is optional and only added on `mode: 'prediction'`, the `results`/`upcoming` variants and any older consumer are unaffected — the frontend test `omits the basis block entirely for a response without metrics` confirms a metrics-less response renders the prior UI unchanged.

### Explainable "Prediction basis" in the panel

`PredictionMetricsBlock` renders only when `prediction.metrics` is present, formats a non-null win pct as `(pct * 100).toFixed(1)%`, and renders the `null` case through the `prediction.metrics.unknown` message ("Not available" / "データなし") rather than letting `null * 100` surface as `NaN`. The component test asserts the `NaN` string never appears for a null underdog, which is the concrete guard against the obvious formatting bug. Strings are localized in both EN and JA via new `prediction.metrics.*` keys, and the e2e spec asserts the JA title `予測の根拠` plus the formatted `60.5%`/`58.0%` values against the fixture — covering criterion 3 end to end. The e2e change also tightened the favorite-name assertion to `{ exact: true }` so it no longer collides with the new `{team}: {pct}` basis line, a correct fix for a real selector ambiguity the feature introduced.

### Test coverage and the one gap

The pure aggregator (7 cases), the service wiring (3 new cases: live-fetch+write-back, reject→neutral, cache-hit short-circuit), and the frontend block (populated, null-handling, metrics-absent) are all covered, and backend tests run green (92 passing). The gap is `fetchStandings` itself: its non-200 branch (constructing `MlbApiError`) and the raw `fetch` network failure are never driven by a `fetch`-mocked unit test — they are only reached transitively when the service test rejects the injected `fetchStandings`. The real wrapper's status handling is therefore unverified. This mirrors the pre-existing `fetchPostseasonSchedule`, which also has no direct test, so it is not a regression, just an unclosed corner of the new surface.
