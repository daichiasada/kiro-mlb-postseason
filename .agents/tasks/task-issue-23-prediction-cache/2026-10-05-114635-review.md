# Prediction response caching with Bedrock throttling and EMF cost metrics (v1)

Issue #23 adds a DynamoDB-backed cache for `mode:'prediction'` responses so a repeated request for the same series situation skips the billable Bedrock narrative call, plus HTTP API throttling and CloudWatch EMF cache/cost metrics. The cache key is a pure, deterministic string built from the series id, both win counts, language, model id, and resolved accuracy; a change in either win count (a game result update) produces a different key and so invalidates the cache without any explicit delete. The cache lookup/write wraps only the final billable branch of `getPrediction`, sitting after the results-only-season, series-final, and not-started short-circuits. A 15-minute TTL is a backstop, and throttling (20 req/s, burst 40) caps the request rate on the public endpoint.

Watch for: the TTL and `!tableName`/mode-guard/read-guard branches in the new store methods are untested at the store level — the service tests use an in-memory stub that never exercises them (likely). The `$default` stage throttle applies to every route, not just `/prediction` (confirmed, benign). Criterion 2 is tested for "a fresh Bedrock call happens" but not for "the response actually changed" (confirmed, minor).

**Verdict**: APPROVED

## High-level view

All three acceptance criteria are genuinely met. Criterion 1 (repeat request skips Bedrock) is enforced by a cache lookup that returns the stored `PredictionResponse` before `predict()` or `generateNarrative()` run, and is covered by a test asserting the second call makes zero additional Bedrock invokes. Criterion 2 (result update invalidates) is realized structurally: the win counts are part of the key, so a changed score maps to a new key and forces a recompute — verified by a test that mutates `high.wins` between calls. Criterion 3 (throttle assertion) is a CDK template assertion checking the exact `ThrottlingRateLimit=20` / `ThrottlingBurstLimit=40` on the `$default` stage.

The lookup sits strictly after the three Bedrock-free short-circuits and after model/language/accuracy resolution, so results-only, series-final, and upcoming responses are never read from or written to the cache. The write-back path additionally guards on `response.mode === 'prediction'` in the store — correct, but only reachable in production code, not in tests.

The key's accuracy component is the one place where correctness depends on an invariant elsewhere: the key uses `accuracy ?? DEFAULT_ACCURACY`, while `predict()` is called with the raw `accuracy`. These agree only because `predict()` independently defaults undefined/non-finite accuracy to 0.5, and because the handler's `parseAccuracy` collapses any non-finite input to `undefined` before it reaches the service. The chain holds, and there is a test for the undefined-vs-0.5 equivalence.

The metrics are emitted via EMF stdout with empty dimensions (series id carried as a plain property), so no new IAM is required and cardinality stays bounded. The emitter never throws. Throttling is set through the L1 `CfnStage` escape hatch and applies to the whole API, which is a slightly broader protection than the "protects /prediction" framing in the docs but is a reasonable choice.

The remaining gaps are test coverage of the store methods and a slightly thin criterion-2 assertion, not behavioral defects.

### Win-count-in-key as the invalidation mechanism

There is no explicit cache delete anywhere; invalidation is purely a function of the key changing. `getPrediction` sources the win counts from the freshly resolved `series.high.wins` / `series.low.wins` on every call, so once `getBracket` refreshes an updated score the next request computes a new key, misses, and writes a new item while the old one expires under the 15-minute TTL. There is no window where a stale key is served after the situation changed, because the stale situation is literally a different key. `predictionCacheKey.test.ts` pins the exact format string and asserts each component independently changes the key, making the invalidation contract regression-proof at the key level.

### Accuracy resolution: two code paths that must agree

The key is built from `resolvedAccuracy = accuracy ?? DEFAULT_ACCURACY`, but `predict()` on the miss path receives the raw `accuracy` (possibly `undefined`). The collapse is sound only because `predict()` independently defaults its parameter to `DEFAULT_ACCURACY` and coerces any non-finite value to it. A second hazard is the key's `String(accuracy)` component: the handler's `parseAccuracy` returns `undefined` (never `NaN`) for malformed input, so the key can never gain a `"NaN"` component that would split the cache. The equivalence is covered by the "undefined maps to the same key as explicit 0.5" test.

If `predict()` were ever changed to treat `undefined` differently from `0.5`, the key would still collapse them and the cache would serve one for the other. That coupling is implicit; a comment already flags it, which is the right mitigation short of threading `resolvedAccuracy` into `predict()` directly.

### Cache placement relative to the short-circuits

```
getPrediction
  ├─ isResultsOnly(season)        → mode:'results'   (no cache, no Bedrock)
  ├─ series.status === 'final'    → mode:'results'   (no cache, no Bedrock)
  ├─ !series || !hasStartedSeries → mode:'upcoming'  (no cache, no Bedrock)
  └─ resolve model/lang/accuracy
       └─ cacheKey
            ├─ HIT  → return cached        (0 Bedrock)   ◄ criterion 1
            └─ MISS → predict + narrative  (1 Bedrock) → putCachedPrediction
```

The lookup is below all three short-circuits, so the non-prediction modes never touch the cache on read. On write, `putCachedPrediction` only ever receives a `mode:'prediction'` response from this path, and the store still re-checks `response.mode !== 'prediction'` and bails. That guard can't be hit from the current caller but is cheap insurance against a future caller that forwards a non-prediction response.

### EMF metrics and cost accounting

`emitCacheMetric` writes one EMF line per request: `PredictionCacheHit=1`/`BedrockInvokeCount=0` on a hit, `PredictionCacheMiss=1`/`BedrockInvokeCount=1` on a miss. Only one of the hit/miss metric names appears per line (the name is chosen dynamically), which is fine for counting but means a dashboard must sum both names to get total requests rather than reading a single series. Dimensions are `[[]]` (empty) and the series id rides as a plain property, so there is no high-cardinality explosion and no `cloudwatch:PutMetricData` IAM.

The miss metric is emitted before `generateNarrative` runs and unconditionally records one invoke; the code comments that the deterministic fallback still counts as one attempt. That is an honest accounting choice — `BedrockInvokeCount` measures attempts, not successes. `emf.test.ts` covers hit shape, miss shape, and the swallow-on-sink-error guarantee.

### Throttling via the L1 escape hatch

`httpApi.defaultStage!.node.defaultChild as CfnStage` reaches the implicit `$default` stage's L1 resource to set `defaultRouteSettings` because the L2 `HttpApi` does not surface it. `DefaultRouteSettings` is an API-wide default, so bracket, standings, and game-detail routes are throttled at the same 20/40 as `/prediction`. The intent is to cap Bedrock cost, and `/prediction` is the only Bedrock-touching route, but the net effect is broader than the docs suggest. The `stack.test.ts` assertion matches the exact values via `Match.objectLike`, so removing the escape hatch or changing the numbers would fail the test — a meaningful guard for criterion 3.

### Test coverage gaps

The service-level criterion-1 and criterion-2 tests are meaningful and would fail if the cache lookup or the win-count-in-key were reverted. Two gaps remain. First, the store methods (`getCachedPrediction`/`putCachedPrediction`) are only exercised through an in-memory `Map` stub, so the real DynamoDB branches — `!tableName` no-op, the `mode !== 'prediction'` write guard, the `!item.prediction` read guard, and the TTL arithmetic — have no coverage. Second, the criterion-2 test asserts a second Bedrock call fires on a win-count change but does not assert the returned prediction differs, so a hypothetical regression that recomputes yet still serves the prior value would pass.
