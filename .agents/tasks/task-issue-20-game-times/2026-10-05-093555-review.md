# Local-timezone game start times, today/tomorrow section, and .ics export (Issue #20) — review (v1)

The aggregation used to truncate `gameDate` to its date part, dropping the first-pitch time and, for Japan viewers, sometimes shifting the displayed day. This change preserves the full start instant end to end: `GameResult` gains two optional fields (`startTime`, `timeTbd`) with `date` left untouched, the backend derives them in `aggregateBracket`, and all display is done by pure, injected-clock/zone frontend helpers (`gameTime.ts`, `upcomingGames.ts`, `ics.ts`) feeding `SeriesCard`, `SeriesDetailPage`, and a new `UpcomingGames` section on the home page. The `.ics` download is entirely client-side — no new endpoint or infra. All three acceptance criteria are met and the helpers are genuinely deterministic (zones/clock pinned in tests).

Watch for: the midnight-UTC placeholder rule (`hasNoTimeOfDay`) will mis-classify a game that *legitimately* starts at exactly `00:00:00Z` as TBD and hide its real time (confirmed — a correctness edge, low real-world frequency for MLB first pitches); and a game that is "today" but already underway renders a `0d 0h 0m` countdown while still appearing in the upcoming list (confirmed — minor display oddity, not a correctness break).

**Verdict**: APPROVED

## High-level view

The shared-contract change is strictly additive: `date` keeps its date-only `YYYY-MM-DD` shape and the two new fields are optional, so the bundled 2024/2025 seed brackets (which carry neither) and any date-only consumer keep working. The backend sets `startTime` to the verbatim `gameDate` for a timed game and omits it when TBD, matching criterion 1.

TBD detection fires on either the API's explicit `status.startTimeTBD` flag or a `gameDate` with no meaningful time-of-day — an exact midnight-UTC placeholder or an unparseable value. The midnight-UTC heuristic is the only soft spot: it cannot distinguish the API's not-yet-scheduled placeholder from a real first pitch that happens to land on `00:00:00Z`, so such a game loses its real time and renders "Time TBD".

Timezone conversion goes through `Intl.DateTimeFormat` with per-language formats (`en-US` 12-hour, `ja-JP` 24-hour), both carrying weekday/month/day so the local date is unambiguous after conversion — this is what fixes the date-shift bug, and the tests prove it with an instant that is a different calendar day in Tokyo vs New York. Zone and locale are injected, so the helpers stay deterministic off-Japan.

The today/tomorrow section buckets by comparing each game's *local* calendar day against now's local day in the injected zone, skipping TBD/undefined-start games, and renders nothing when the list is empty — safe to mount unconditionally. The countdown clamps past/unparseable instants to zero.

The client-side `.ics` is a correct minimal single-VEVENT VCALENDAR: UTC basic-format `DTSTART`/`DTEND`, deterministic `DTSTAMP`, RFC5545 text escaping, CRLF joins, 180-minute default duration. The download path is guarded so jsdom/non-browser is a no-op.

### Additive shared contract — `date` is genuinely untouched

`aggregateBracket` keeps `date: game.gameDate.slice(0, 10)` verbatim and layers the new fields on with a spread: `...(timeTbd ? { timeTbd: true } : { startTime: game.gameDate, timeTbd: false })`. The committed 2024/2025 seed brackets are already-aggregated `Bracket` JSON (they store `date`, not `gameDate`) and carry zero `startTime` fields, confirmed by grep — so the aggregator never re-runs over them, there is no re-classification of seed data, and the `UpcomingGames` section renders nothing for those seasons because every seed game lacks a concrete `startTime`.

### TBD detection and the midnight-UTC edge

```ts
function hasNoTimeOfDay(gameDate: string): boolean {
  const parsed = new Date(gameDate);
  if (Number.isNaN(parsed.getTime())) return true;
  return (
    parsed.getUTCHours() === 0 && parsed.getUTCMinutes() === 0 &&
    parsed.getUTCSeconds() === 0 && parsed.getUTCMilliseconds() === 0
  );
}
const timeTbd = game.status?.startTimeTBD === true || hasNoTimeOfDay(game.gameDate);
```

The explicit `startTimeTBD` branch is the reliable signal (`client.ts` `RawGame.status` now carries the optional flag, passed through from the raw JSON). The midnight-UTC fallback has an unavoidable false-positive: any game whose true first pitch is exactly `00:00:00Z` — a normal evening slot west of UTC (e.g. 20:00 EDT the prior day, or a 09:00 JST morning game) — is indistinguishable from the not-yet-scheduled placeholder and is hidden behind "Time TBD" with no calendar export. MLB first pitches rarely land on the UTC hour boundary, so this is not blocking, but it is a real behavioral gap worth tightening (gate the midnight rule on a non-live `abstractGameState`, or drop it in favor of the explicit flag alone). The assumption that the live API emits `T00:00:00Z` for unscheduled games is only asserted by a synthetic test, not verified against a live payload.

### Intl EN/JA conversion and the date-shift fix

`formatStartTime` renders through `Intl.DateTimeFormat` with the injected `timeZone`, `en-US` + `hour12: true` vs `ja-JP` + `hour12: false`, and always includes `weekday`/`month`/`day` so the converted *local* date is explicit. The tests pin a single instant (`2024-10-01T18:32:00Z`) that is Oct 2 03:32 in Tokyo but Oct 1 14:32 in New York and assert both the shifted day and the per-locale clock, so they would fail if the formatter dropped the date parts or the locale/hour12 split were reverted. The TBD/undefined/unparseable paths return the injected `tbdLabel` rather than throwing, and `resolveTimeZone` falls back to `'UTC'` when `Intl` is unavailable.

### Today/tomorrow bucketing — local-day comparison, empty-safe

`bucketGameDay` resolves both the game instant and `now` to a `{y,m,d}` triple *in the injected zone* via `en-CA` `formatToParts`, then diffs them through a UTC day-number counter used purely as arithmetic. The test that the same UTC instant buckets `tomorrow` in Tokyo but `today` in New York would fail under a naive UTC-date comparison, so it has teeth. `selectUpcomingGames` skips `timeTbd`/undefined-start games, and `UpcomingGames` returns `null` on an empty list, so it is safe to mount unconditionally in `HomePage`'s started branch.

One display oddity: a game whose local day is today but whose start is already in the past still passes the `today` filter and is listed, while `countdownParts` clamps it to `0d 0h 0m`. The copy "Starts in 0d 0h 0m" then misrepresents an in-progress/finished-today game. Not a correctness bug in the pure helpers (clamping is the right call to avoid negatives), but the UI could distinguish a zero countdown as "started/live".

### Client-side .ics correctness

`escapeText` handles backslash→semicolon→comma→newline in the correct order, `DTSTAMP` falls back to `start` rather than `Date.now()`, and the escaping/CRLF/throw-on-unparseable-start contracts are all asserted (the no-bare-LF regex and the `a;b\c\nd → a\;b\\c\nd` case). `downloadIcs` in `SeriesCard` guards on `URL.createObjectURL`/`document` so jsdom is a no-op, and the calendar affordance is omitted for TBD/undefined-start games.

### UI wiring and regression surface

The new "Add to calendar" button in `SeriesCard` is an inner control, and the existing `event.target !== event.currentTarget` guard on the card `<article>` already ignores inner-control key events, so the roving-tabindex / Enter-Space activation model is not at risk of a double-fire. `SeriesDetailPage` threads `lang`/`timeZone` into `DetailGame` without altering score/winner logic. The `MessageKey` union gains all ten new keys populated in both EN and JA, so a missing translation is a compile error. Existing date-based rendering and seed parsing are unaffected.

### Test coverage

Pure helpers are well covered across EN/JA, Tokyo/New-York, and the TBD/past/unparseable edges, and the aggregate tests assert the three-way `date`/`startTime`/`timeTbd` outcome for timed, explicit-TBD, and midnight-placeholder games plus a property-based invariant that `timeTbd` and `startTime` are mutually exclusive. Component and e2e tests confirm the rendered affordances without asserting exact clock values (runner zone unknown). I re-ran the three new helper suites: 27 passed, deterministic.

Not tested: a game that legitimately starts at exactly `00:00:00Z` (the false-positive edge above — no test pins the intended behavior either way); the "today-but-already-started" zero-countdown rendering; and `buildIcs` with a multi-day/odd `durationMinutes` crossing a month boundary (the UTC arithmetic is sound, but there is no fixture for it).
