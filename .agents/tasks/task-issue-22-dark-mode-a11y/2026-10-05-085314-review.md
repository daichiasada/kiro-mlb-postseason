# Dark mode + bracket accessibility for the postseason site (v1)

Issue #22 adds a System/Light/Dark theme (following `prefers-color-scheme`, overridable by a header toggle persisted to `localStorage` under `mlb.theme`), auto-selected black/white badge text computed from WCAG contrast against each team's brand color, and full keyboard navigation plus screen-reader labelling of the bracket. The approach splits a pure, framework-free core (`theme.ts`, `readableTextColor.ts`) from thin React glue (`ThemeContext.tsx`, `ThemeToggle.tsx`), applies the resolved theme as `data-theme` on `<html>` so every route inherits it, and defines light/dark palettes entirely in CSS variables. The three acceptance criteria — AA contrast across all team colors, zero serious axe violations, legibility in both themes — are each backed by a test (an all-teams contrast unit test, axe scans in both themes across three surfaces, and a dark screenshot).

Watch for: a keyboard/mouse activation asymmetry on series cards — Enter/Space on the card body navigates or selects, but a mouse click on the card body does nothing (only the inner link/button is clickable) (confirmed). The flash-prevention bootstrap in `index.html` re-implements the storage key and resolve logic as inline literals, decoupled from `theme.ts`, with no test guarding that they stay in sync (likely). No blocking defects found.

**Verdict**: APPROVED

## High-level view

The theme model splits a pure core (`theme.ts`: types, storage key, guarded read/store, `resolveTheme`) from React glue (`ThemeContext.tsx`), which subscribes to `matchMedia` so a `'system'` preference flips live on an OS change and writes `data-theme` to the document root. An inline script in `index.html` paints the right palette before React mounts to avoid a flash — but it duplicates the `mlb.theme` key and the resolve logic as literals, so a future rename in `theme.ts` would silently break first-paint without any test failing.

Badge text color is derived, not hardcoded: `readableTextColor` implements the WCAG luminance/contrast formulas and picks whichever of black/white clears the higher ratio against the team's primary fill. The all-team-colors unit test asserts the chosen text clears AA (≥4.5:1) on every team's primary and secondary plus the fallback color, so a brand-color change that breaks contrast fails CI.

Bracket keyboard support uses a roving-tabindex model over a deterministic `[column][row]` grid: exactly one card is tabbable, arrow keys move focus (clamped at edges, no wrap), Home/End jump within a column, and Enter/Space on the card activates it — opening the detail route for a finished series or selecting a predictable one. Activation bails when the event originates on an inner control so the card never double-fires. The gap is that this makes the whole card keyboard-activatable while mouse users must still click the inner link/button, and a card in a state that is neither final nor predictable is focusable but does nothing on Enter.

Contrast in dark mode was handled by introducing a distinct `--heading` variable for navy-as-text (brightened to `#8fb4f2` in dark, ≥5.9:1) separate from `--navy` as a fill, so headings/links/game-numbers clear AA without lightening the navy gradients. A `--focus-ring` variable keeps the focus outline legible in both palettes, and `color-scheme` is set per theme so native form controls match.

### Theme resolution and live OS reactivity

`resolveTheme` is pure (`'light'`/`'dark'` map to themselves, `'system'` defers to the passed `systemPrefersDark` flag), which keeps the OS dependency out of the resolver and makes the `'system'` branch directly unit-testable. `ThemeContext` subscribes to the `(prefers-color-scheme: dark)` media query, re-syncing on subscribe and on every `change` event, so toggling the OS theme while the preference is `'system'` flips the app without a reload.

The flash-prevention bootstrap is where the clean layering breaks down. The inline `<script>` in `index.html` must run before the module graph loads, so it re-implements the resolve rule and the `'mlb.theme'` key as literals. That is unavoidable for a pre-paint script, but nothing ties it back to `THEME_STORAGE_KEY` or `resolveTheme`: a future rename of the key, or a change to how `'system'` resolves, would leave the first paint diverging from the mounted app with no test catching it. The axe spec seeds the preference with `addInitScript` and asserts the final `data-theme`, which exercises the provider's apply path but not the inline script's own resolution on a cold first paint.

### Auto-contrast badge text across all teams

`readableTextColor` is the mechanism behind acceptance criterion (1). It parses `#rgb`/`#rrggbb` (with a safe black fallback for malformed input), computes WCAG relative luminance, and returns whichever of black/white yields the higher contrast ratio, resolving ties to black. The all-team-colors test iterates every id in the color table and asserts the chosen text clears AA (≥4.5:1) against both the primary and secondary fills, plus the `DEFAULT_COLOR` fallback via an unknown id — so this is a genuine regression guard: if a team's brand color were edited to a mid-tone where neither black nor white clears 4.5:1, the test fails rather than silently shipping an illegible badge. One honest limitation worth noting: the guarantee is only as complete as the hardcoded `TEAM_IDS` list in the test, which is maintained in parallel with the color table rather than derived from it.

### Bracket roving-tabindex navigation

```
          col 0            col 1            col 2
        Division          Championship      World Series
        ┌────────┐        ┌────────┐        ┌────────┐
 row 0  │ card*  │ ──►    │ card   │ ──►    │ card   │
        └────────┘        └────────┘        └────────┘
 row 1  │ card   │
        └────────┘
   * exactly one card has tabindex=0; arrows move it, Tab enters/leaves
```

Focus management is driven off the `[column][row]` grid from `buildRoundColumns`. The active cell is clamped against the current column/row counts, so a season switch that changes the shape of the bracket always leaves exactly one tabbable card rather than a dangling reference. Arrow keys clamp at the edges (no wrap), which the e2e verifies by pressing ArrowDown on a single-row column and asserting focus does not move. `preventDefault` on handled keys stops the page from scrolling under the navigation.

The activation contract lives on the card: Enter/Space opens the detail route for a final series or calls `onSelect` for a predictable non-final one, and the handler bails when `event.target !== event.currentTarget` so a key pressed on the toggle button, detail link, or predict button keeps its native behavior instead of double-firing. Two behavioral edges fall out of this design. First, keyboard activation covers the whole card while mouse activation does not — clicking the card body does nothing; a mouse user must hit the "View detail" link or the predict button. That is not a regression (mouse paths still work) but it is an asymmetry a reviewer should be aware of. Second, a card that is neither final nor predictable is still focusable with a roving tabindex, yet Enter/Space is a no-op for it; this is harmless only if that state cannot occur on a rendered bracket.

### Screen-reader labelling

Each card carries an `aria-label` built from `series.cardLabel` naming both clubs, the localized status, best-of, and the score, and the grid is wrapped in a `role="group"` whose label (`bracket.gridLabel`) states the keyboard usage ("use the arrow keys… press Enter…"). Both strings exist in EN and JA, and the keyboard e2e asserts the Japanese label announces both teams, the localized status, and the score, so the labelling is checked against real rendered output rather than assumed. The gridLabel's promise ("open a finished series or select a series to predict") matches the card's actual Enter behavior.

### Dark palette and contrast fix

The contrast fix hinges on splitting the navy-as-text role from navy-as-fill: `--navy` fills gradients and badges, so brightening it would wash out those surfaces, while headings/links/game-numbers on dark surfaces needed to clear AA. The new `--heading` variable carries only the text role and is lifted to `#8fb4f2` (≥5.9:1 on dark surfaces) in dark, equal to `--navy` in light so light mode is unchanged. `--focus-ring` is themed per palette and applied via `:focus-visible`, so the focus indicator stays legible on both backgrounds, and `color-scheme` is declared per theme so native controls and scrollbars match.

### Test coverage

The three criteria are each pinned: the all-teams contrast unit test (criterion 1), seven axe scans across home/detail/accuracy in both light and dark asserting zero serious/critical violations (criterion 2), and a dark-mode screenshot plus explicit visibility assertions on the AL/NL league marks (criterion 3). Theme behavior is covered end to end — `resolveTheme` purity, storage round-trip and invalid-value rejection, and a provider-level test proving a Dark click updates preference, resolved theme, `data-theme`, and `localStorage` together. Keyboard nav has both unit (roving tabindex, ArrowDown/ArrowRight movement, Enter-navigates vs Enter-selects, inner-control bail-out) and e2e coverage.

Not tested: the inline flash-prevention script's own first-paint resolution (only the post-mount `data-theme` is asserted); the keyboard/mouse activation asymmetry on the card body; and the derived-vs-hardcoded team-id list means a newly added team would need a manual edit to the test to be covered.

### Specs and READMEs

The spec additions (requirements/design/tasks) and both READMEs describe the as-built behavior accurately: the `mlb.theme` key and its `system|light|dark` values, live `prefers-color-scheme` reactivity, the inline no-flash script, the roving-tabindex arrow-key model with Enter-to-open, the computed badge text color, and the axe-in-both-themes verification. README.md and README.ja.md are in sync on all of these points.
