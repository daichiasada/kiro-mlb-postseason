# Share permalinks + per-series OGP — public-origin fix (v2)

The v1 review returned NEEDS_CHANGES over one blocking issue: the share Lambda baked the execute-api host into `og:url`/`canonical`/`og:image`/the redirect because the `/share*` and `/og*` CloudFront behaviors use `ALL_VIEWER_EXCEPT_HOST_HEADER` and no public origin was ever supplied. Fix commit `b0dd5eb` resolves it with a viewer-request CloudFront Function (`ShareSiteOriginFn`) that copies the viewer `Host` into an `x-site-origin` request header before Host is stripped; `getShareHtml.resolveOrigin` now reads `x-site-origin` ahead of the raw Host. The same commit also makes the copy fallbacks carry the disclaimer, corrects a misleading doc comment, and documents the CORS wildcard honestly.

Watch for: nothing blocking. One **possible** edge case — the share HTML is cached by seriesId+wins+lang with no origin component, so a cache entry built on a non-CloudFront path (no `x-site-origin`) could be served to later CloudFront hits; not reachable in the deployed topology since all `/share*` traffic flows through the function.

**Verdict**: APPROVED

## High-level view

The origin fix is acyclic by construction. A static `cloudfront.Function` at viewer-request copies `Host` into `x-site-origin`; because the function references no other construct it does not create the CloudFront↔Lambda cycle that blocked injecting `SITE_ORIGIN` as a Lambda env. The function association rides on the shared `apiBehavior` object applied to all four patterns (`/og`, `/og/*`, `/share`, `/share/*`), so both behaviors are covered, and the header name/casing the function sets (`x-site-origin`) matches the case-insensitive lookup in the handler. `resolveOrigin` now feeds a single resolved origin into both the canonical permalink and the OG-image URL, so `og:image` traverses the cached `/og*` behavior rather than hitting API Gateway directly — which also closes the v1 caching concern as a consequence.

Coverage reproduces the production failure mode rather than the happy path: the new handler test sends `Host=…execute-api…` with `x-site-origin` present and asserts the public cloudfront.net origin appears in `og:url`/`og:image` while `execute-api` appears nowhere, so it would fail on a revert of the handler change. The stack test asserts both that a CloudFront Function containing `x-site-origin` exists and that the `/share` and `/og` behaviors carry a viewer-request `FunctionAssociation`.

The remaining three v1 items are settled: the copy and manual-copy fallbacks now share the same `title + disclaimer + URL` payload as the Web Share path (manual copy switched to a multi-line `<textarea>` to preserve newlines), with tests asserting the localized disclaimer in both; the CORS wildcard keeps a comment that states the cycle-avoidance reason truthfully; and the handler doc comment no longer claims `SITE_ORIGIN` is injected by CDK.

<summary>Details</summary>

### x-site-origin: acyclic origin propagation

The blocking v1 defect was that `resolveOrigin` fell through to `header('host')` in production, and that Host is the execute-api domain because `ALL_VIEWER_EXCEPT_HOST_HEADER` strips the viewer Host before the origin request. The fix inserts a lookup for `x-site-origin` ahead of `host`:

```
SITE_ORIGIN env  ->  x-site-origin header  ->  X-Forwarded-Proto + Host  ->  localhost
```

The header is populated by a viewer-request `cloudfront.Function` whose body copies `request.headers.host.value` into `request.headers['x-site-origin'] = { value: 'https://' + host }`. Viewer-request runs before the origin request policy, so the Host is still the public one the viewer used (distribution domain or a custom CNAME). The function is inline and references no other construct, so it introduces no dependency edge — the reason a `SITE_ORIGIN` Lambda env or a distribution-domain custom origin header could not be used without a synth cycle. The infra test confirms synth stays clean (15 unit tests pass).

The association is defined once on `apiBehavior` and applied in the `for (const pattern of ['/og', '/og/*', '/share', '/share/*'])` loop, so every share/OG behavior gets the viewer-request function — not just one. `resolveOrigin` reads headers case-insensitively, which matches the lowercase `x-site-origin` the function emits.

Both URL surfaces derive from the one resolved origin: `buildSeriesPermalink({ origin, … })` for `canonical`/`og:url`/redirect and `buildOgImageUrl({ apiBase: origin, … })` for `og:image`. With the origin now the public site, the `og:image` URL points at `https://<site>/og?…`, which routes through the cached `/og*` behavior — resolving the v1 edge-cache-bypass observation without separate work.

### Cache key omits origin

`shareCacheKey` encodes seriesId + high/low wins + lang, and a cache hit returns the stored HTML verbatim without re-resolving the origin. If the first population of a given key happened on a request without `x-site-origin` — a direct execute-api hit, a smoke test, or a future second CloudFront domain — the baked-in origin would be wrong for every subsequent reader of that key, including real CloudFront hits. In the current deployment this is not reachable: `/share*` is only served through the distribution, where the viewer-request function always sets the header, so the first and all later populations carry the public origin. Flagged as `possible` because it becomes real the moment a second origin or a non-CloudFront ingress is introduced; a comment on the cache key noting the origin-independence assumption would be enough.
