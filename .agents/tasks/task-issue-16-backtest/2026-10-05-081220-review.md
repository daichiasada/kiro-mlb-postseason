# Deterministic backtest engine and Model-accuracy page for the prediction model (v1)

Issue #16 asks the completed 2024/2025 seed brackets to be replayed through the numeric prediction model ("predict at the end of each game") and scored with hit rate, Brier, and calibration, surfaced on a localized "Model accuracy" page with an accuracy-value comparison. The implementation relocates the pure `predict()` into `@mlb/shared` (backend re-exports it unchanged), adds a pure `backtest.ts` engine that imports only `predict`, domain types, and the seed JSON, and builds a client-side `/accuracy` page that computes everything in the browser. The three acceptance criteria are genuinely met: fixed hit-rate/Brier literals pinned in unit tests act as a real regression guard, metric definitions are present in the UI and both READMEs in EN and JA, and the engine's import graph structurally excludes Bedrock/DynamoDB/network.

Watch for: the headline hit rate and Brier include the "end of the deciding game" snapshot, which is an already-clinched, guaranteed-correct prediction — this inflates the reported numbers and is not caveated anywhere (confirmed). The calibration bars visualize bucket frequency rather than predicted-vs-empirical, so the one metric whose point is a visual comparison isn't shown as one (confirmed, minor).

**Verdict**: APPROVED

## High-level view

The predict relocation is behavior-preserving in the strongest sense: the function body moved to `shared/src/predict.ts` is byte-identical to the old `backend/src/predict/model.ts`, and the backend file is now a pure re-export, so every existing backend import path and the untouched backend predict tests still exercise the same code.

The backtest engine recomputes partial win counts from the first k games rather than trusting stored totals, rounds metrics to a fixed precision so the pinned test literals are stable, and the Bedrock-not-called criterion is satisfied structurally — the transitive import set is `predict` + types + seed JSON, with no AWS/network dependency reachable.

The scoring semantics include one snapshot per game including the final, clinching game. At the deciding game the series is already won, the clinching team's progress signal is maxed, and the favorite is trivially the eventual winner — so every series contributes at least one guaranteed hit at maximum confidence. This matches the authored spec (k=N is deliberately `status: 'final'`), but it means the headline metrics blend decided snapshots with genuine mid-series predictions and read better than the model's actual predictive skill.

The page and docs are complete and accurate. 34 new i18n keys carry EN and JA copy, the Brier and calibration definitions on the page match the engine's math and are mirrored verbatim in README.md and README.ja.md, and the metrics are computed client-side with no backend endpoint or infra change. Unit, component, and e2e layers all assert the three metrics and the definition text; the change is cleanly scoped with no unrelated files.

### predict() relocation is byte-identical

The function body in `shared/src/predict.ts` hashes identically to the pre-change `backend/src/predict/model.ts` body (verified by comparing the `export function predict` … closing-brace span). The clamp bounds (0.5/0.95), the `f = 2*accuracy` sharpening around the 0.5 floor, the 4-decimal rounding, and the non-finite-accuracy fallback are all carried over unchanged. `backend/src/predict/model.ts` now re-exports `predict`, `teamName`, the accuracy constants, and the `PredictionResult`/`WinPctMap` types from `@mlb/shared`, so `backend/src/index.ts`, `service/bracketService.ts`, `bedrock/narrative.ts`, `store/dynamo.ts`, and `predict/standings.ts` resolve the same symbols. `predict.ts` imports the accuracy constants internally and does not re-export them, avoiding a barrel collision with `./accuracy.js` in `shared/src/index.ts`.

### Deterministic fixed-number test is a real regression guard

`backtest.test.ts` pins concrete literals — 2024 `0.906977 / 0.134132 / 43`, 2025 `0.744681 / 0.194365 / 47`, combined `0.822222 / 0.165587 / 90` — all at accuracy 0.5. Because these flow from `predict()` over the seed data, any change to the prediction math, the sharpening transform, the rounding, or the seed JSON shifts them and fails the suite. The `accuracy = 0` case asserts Brier is exactly `0.25` (every favorite probability collapses to 0.5, squared error `(0.5-1)^2`), which independently pins the sharpening floor. Calibration-count invariants (bins sum to `sampleCount`; all samples land in `[0.5,0.6)` at accuracy 0) and the empty-bracket contract (`sampleCount 0`, no NaN) are covered, and the property test bounds `hitRate`/`brierScore`/`empiricalWinRate` in `[0,1]` across 100 random accuracies over both real brackets.

### "Predict at end of game k" includes the decided game

For each final series the engine sorts games by `seriesGameNumber`, and for k in 1..N builds a partial series whose `high.wins`/`low.wins` are recomputed from the first k games (stored totals are not trusted) with status `in_progress` for k<N and `final` at k=N. The eventual winner is the side with the greater final win total. The subtlety is k=N: the deciding game is already clinched, so the winning side's progress signal is `wins/clinch = 1.0`, the model favors it at the 0.95 ceiling, and the snapshot is a guaranteed hit.

Quantified over 2024+2025 at accuracy 0.5:

```
final-game (k=N) snapshots : 22/22  = 100.0%  (always correct, by construction)
mid-series (k<N) snapshots : 52/68  =  76.5%  (the genuinely predictive part)
combined (reported)        : 74/90  =  82.2%
```

So 22 of 90 samples are decided outcomes rather than predictions, and they pull the headline hit rate up ~5.7 points (and improve Brier correspondingly). This is faithful to the authored semantics in FEAT-002, and the README methodology says "using only the games played so far" — technically true at k=N, but a reader won't infer that the last snapshot is a settled result. A one-line caveat, or a mid-series-only cut of the metric, would make the number honest about predictive skill without changing the engine.

### Brier and calibration math match the published definitions

`brierScore = mean((probOfEventualWinner - 1)^2)` where `probOfEventualWinner` is `favoriteWinProbability` when the favorite won else `1 - favoriteWinProbability`. The UI and both READMEs define it as "the mean squared error between the predicted probability of the eventual series winner and 1," which is exactly this quantity. It is a single-outcome squared error (not the two-term two-class Brier), but it is internally consistent and the definition text describes precisely what is computed. Calibration uses fixed edges `[0.5,0.6,0.7,0.8,0.9,0.95]` with the last bin right-inclusive so the 0.95 clamp ceiling lands in it; empty buckets report `null` means rather than 0, and populated buckets report mean predicted probability and empirical win rate — matching the "compare mean predicted vs actual win rate per bucket" definition.

For criterion 3, the structural guarantee is concrete: `backtest.ts` imports only `./predict.js`, `./types.js`, `./seed/index.js`; `predict.ts` imports only `./accuracy.js` and `./types.js`; a grep over that transitive set finds no AWS SDK, DynamoDB, Bedrock, or network/`fetch` dependency, so Bedrock cannot be reached by construction rather than by convention.

### Calibration visualization encodes frequency, not calibration

In `AccuracyPage.tsx` the bar fill width is `predictedCount / maxBucketCount`, i.e. how many samples fell in each bucket. The predicted-vs-empirical pairing that defines calibration is rendered only as text and in the per-row `aria-label`/`binLabel`. An unused `data-empirical-width` attribute hints the empirical rate was meant to be visual. The accessible text is complete, so no information is lost, but the chart doesn't visually express the metric it's labeled with.

### Localization, routing, and test coverage

34 `accuracy.*` keys are added to the `MessageKey` union with both EN and JA strings; the Brier and calibration definitions are present and accurate in both. The `/accuracy` route is registered before the catch-all, and a localized nav link is added to the HomePage header so the page is reachable in every season. Coverage spans all three layers: the component test asserts the three metric sections, the Brier/calibration definition text, the pinned 0.5 numbers (82.2% / 0.166, per-season 90.7% / 74.5%), the accuracy=0 Brier of 0.250, five calibration buckets with aria-labels, and JA localization; the e2e spec navigates from the nav link, checks all three metrics and both definitions in JA then EN via the toggle, and asserts all five accuracy rowheaders. Not tested: the calibration bar widths / visual rendering (only the text and bucket count are asserted), and there is no explicit assertion that an empty/unknown season renders the "No predictions" empty-bucket copy.
