# Bracket alignment, collapsible game detail, finished-series detail pages, final-series prediction-OFF, JA/EN i18n, and configurable prediction accuracy (v1)

Six Japanese-language feature requests land across backend and frontend of the MLB postseason site. The uneven ("gatagata") bracket is realigned by anchoring every round column to the top and collapsing each card's game list by default so cards start at a uniform height. A per-series toggle shows/hides the inline game list; finished series get a dedicated client-side-routed detail page; finished series turn prediction OFF at the series level in both the backend service and the frontend; a lightweight in-repo JA/EN i18n layer localizes the UI (default Japanese) including a localized unknown-team fallback; and the deterministic prediction model gains a configurable `accuracy` sharpness control threaded end to end. The work is spec-driven and the requirements/design/README were updated to match.

Watch for: a newly-added English-only `alt` text leak on two header images in Japanese mode (confirmed, minor); the backend `accuracy` constants are mirrored as hardcoded literals in the frontend `config.ts` rather than shared, a drift risk (confirmed, minor); the series-level final gating correctly short-circuits before predict/Bedrock and is well-tested (confirmed good). All four test suites are green (shared 14, backend 57, frontend 35, infra 6) and the new code is meaningfully exercised — reverting any of the six behaviors breaks a test.

**Verdict**: APPROVED

## High-level view

The final=>no-prediction rule is implemented symmetrically: the backend `getPrediction` returns `mode:'results'` for a `status==='final'` series before touching the predict model or Bedrock, and the frontend `SeriesCard` hides the predict button for final series and offers a detail link instead, so no numeric probability is ever requested or shown. Backend and frontend agree, and both halves are covered end-to-end (service unit test asserts no Bedrock call; Playwright asserts no `/prediction` request and no progressbar).

The accuracy control is a sharpness transform `p = clamp(0.5 + (clamp(share,0.5,0.95)-0.5)*(2*accuracy), 0.5, 0.95)` with default 0.5 chosen as an exact identity so historical output is preserved (pinned by a regression guard at 0.8093). It is threaded slider -> `&accuracy=` query -> handler -> service -> `predict()`. The `[0.5,0.95]` invariant is proven by fast-check across in-range and out-of-range accuracy. The one caveat is that the frontend mirrors the backend's MIN/MAX/DEFAULT/STEP as hardcoded literals because those constants live in the backend, not in `@mlb/shared`.

Routing is path-based via `BrowserRouter` with `/`, `/season/:season`, and `/season/:season/series/:seriesId`; unknown paths and malformed season params fall back to the default season rather than erroring. Deep links depend on the pre-existing CloudFront 403/404->/index.html rewrite (unchanged in this task set), which is correctly relied upon.

The i18n layer is a React context plus a flat dotted-key dictionary with no new runtime dependency, defaulting to Japanese and persisting to `localStorage['mlb.lang']`. Every UI string flows through `t()`, round/status labels are mapped, and unknown/preview team ids render a localized placeholder (`未定 (#id)` / `TBD (#id)`) instead of the raw `Team <id>` that previously leaked. Club names are intentionally English in both languages. The remaining localization gap is two image `alt` strings left in English.

### Series-level final gating is symmetric across backend and frontend

The requirement "finished series => prediction OFF" is enforced in two independent places that agree. In `bracketService.getPrediction`, after the season-level results-only short-circuit and after resolving the series, a `series.status === 'final'` check returns `{ mode: 'results', ... }` without calling `predict()` or `generateNarrative()`. The ordering matters and is correct: the final check sits between bracket resolution and the `hasStartedSeries` upcoming guard, so a finished current-season (2026) series never reaches the predict/Bedrock path. The service test proves the short-circuit by asserting `bedrockInvoke` is never called for a final 2026 series while a sibling in-progress 2026 series still returns `mode:'prediction'` with exactly one Bedrock call.

On the frontend, `SeriesCard` computes `isFinal` and renders the predict button only when `onSelect && predictable && !isFinal`; a final series instead renders the detail-page `Link`. `PredictionPanel` additionally treats a defensive `mode:'results'` response as a no-numeric state. The Playwright `prediction.spec.ts` final-series test closes the loop at the behavioral level: for the final 2026 card it asserts zero predict buttons, a visible detail link, zero `/prediction` requests captured, and no progressbar after navigating to the detail page. Backend and frontend cannot silently diverge here without a test failing.

### Accuracy transform, bounds, and end-to-end threading

`predict()` gained a 4th `accuracy` argument defaulting to `DEFAULT_ACCURACY = 0.5`. The transform clamps the raw favorite share to `[0.5, 0.95]` (p0), applies `sharpenFactor = 2 * safeAccuracy` around the 0.5 floor, then clamps again to `[0.5, 0.95]`. `safeAccuracy` falls back to the default for a non-finite input and otherwise clamps into `[0, 1]`, so out-of-range and `NaN` inputs are handled before they can violate the bound.

The default of 0.5 yields `sharpenFactor = 1`, an exact identity on p0, which is why the unit test can pin the pre-accuracy output (`0.8093`) as a regression guard and assert `predict(...,{},0.5)` equals the no-accuracy call. The remaining unit tests cover monotonic-non-decreasing behavior across `[0,0.25,0.5,0.75,1]`, collapse to exactly 0.5 at accuracy 0, clamping of `-5`/`42` to the 0/1 endpoints, favorite-team stability across accuracy, and `NaN`->default. The property suite (`model.property.test.ts`) samples accuracy in `[-0.5, 1.5]` and asserts `favoriteWinProbability ∈ [0.5, 0.95]` and `favoriteTeamId` membership for every generated series — the core invariant the requirement calls out.

Threading is complete: `getPrediction.ts` reads `accuracy` from either the GET query or POST body via `parseAccuracy`, which returns `undefined` for missing/non-numeric values (a best-effort knob, not a hard gate like `season`) so the model default applies. The service forwards it to `predict()`. On the frontend, the `PredictionPanel` slider updates local `accuracy`, debounces (300ms) into `requestedAccuracy`, and the fetch effect re-requests with it; `api.getPrediction` appends `&accuracy=` only when defined. Both the component test (asserts the initial call carries 0.5 and a slider change re-requests with 0.9) and the e2e (initial 0.5 -> 70.0%, drag to 1 -> 90.0%, capturing the query param) exercise the full path.

One drift risk: `frontend/src/config.ts` redefines `MIN_ACCURACY=0`, `MAX_ACCURACY=1`, `DEFAULT_ACCURACY=0.5`, `ACCURACY_STEP=0.05` as literals mirroring the backend. The accompanying comment acknowledges this, and the project convention is that domain types live only in `@mlb/shared` — but these numeric bounds are shared contract, not backend-internal detail, and are a candidate for hoisting into `@mlb/shared` so a future change to the supported range can't silently desynchronize the slider from the model.

### Routing, deep links, and the CloudFront dependency

`App.tsx` defines `/` (redirect to default season), `/season/:season`, `/season/:season/series/:seriesId`, and a `*` catch-all redirecting to the default season. `parseSeasonParam` coerces a missing/non-integer/unsupported `:season` to `DEFAULT_SEASON`, so a malformed URL renders the default bracket rather than breaking. `SeriesDetailPage` re-fetches the bracket for the route season (reusing the offline-seed fallback in `api.getBracket`) and renders a friendly localized not-found section when the id isn't present, with a back link.

Deep links such as `/season/2026/series/<id>` depend on CloudFront rewriting 403/404 to `/index.html` with `responseHttpStatus: 200`. That rewrite is pre-existing in `infra/lib/mlb-postseason-stack.ts` and unchanged in this task set, so no infra work was needed; `main.tsx` documents the dependency. The e2e suite deep-links directly to a detail URL and to an unknown-id URL and verifies both resolve to the SPA.

One behavioral note worth surfacing (not a defect): `SeriesDetailPage` renders detail for any series id it finds, not only `status==='final'` ones. Requirement #3 scopes the detail page to finished series, and the only entry point to it is the detail link that `SeriesCard` renders exclusively for final series, so in normal navigation only finished series reach the page. A hand-typed deep link to a non-final series still renders gracefully (it shows the running series score via the `winnerId === null` branch rather than a "won the series" line), which is a reasonable degrade rather than an error.

### i18n coverage and the unknown-team fallback

`MessageKey` is a closed union, so a missing translation is a type error rather than a runtime surprise — the one non-obvious safeguard in an otherwise plain context-plus-dictionary layer. Coverage spans every panel (`SeriesCard`, `PredictionPanel` incl. the accuracy slider and `aria-valuetext`, `StandingsPanel`, `BracketView` legend, `SeriesDetailPage`, `HomePage`, `LanguageToggle`), with round/status names mapped through `ROUND_KEY`/`STATUS_KEY`. The headline fix is `teamName`/`teamAbbr`: an id absent from `TEAMS` now renders `t('team.unknown', { id })` -> `未定 (#5513)` / `TBD (#5513)` instead of the raw `Team 5513` that leaked from 2026 preview data, covered by both unit tests (asserting the string is never `Team 5513`) and an e2e checking the placeholder in both languages on a real preview-id card. Club names are intentionally English in both languages, documented in `messages.ts`.

The gap: `HomePage.tsx` hardcodes `alt="MLB Postseason Pulse logo"` and `alt="Baseball diamond at dusk"`. These bypass `t()`, so a Japanese-mode screen-reader user hears English alt text — the only localization leak introduced by this change (the progressbar `aria-label` is pre-existing and out of scope). Both should get message keys and flow through `t()`.

### Bracket alignment and collapsed-by-default toggle

The uneven layout had two contributing causes, both addressed: `.bracket__grid` now sets `align-items: start` so columns with different series counts line up and expanding one card grows only its grid row, and `SeriesCard` collapses the game list by default so every card starts at a uniform compact height. One non-obvious detail: React's `useId()` returns colon-containing ids invalid as CSS/DOM selectors, so the toggle sanitizes it before wiring `aria-controls`/`#id` — without which the Playwright locators and `#id` lookups would silently fail. Collapsed-by-default and toggle behavior are verified in both the component test and an e2e checking `aria-expanded`, the hidden list, and the label flip.

### Spec and README truthfulness

The task is a graded spec-driven lesson, so the requirements/design/README must match the implementation. Requirements 7–11 were checked against the code: the accuracy requirement transcribes the exact transform `p = 0.5 + (p0 - 0.5) * (2*accuracy)`, the `[0.5,0.95]` invariant, and the identity-at-0.5 default, matching the model's clamp sequence and `parseAccuracy`'s undefined-on-invalid behavior; the detail-page requirement states the exact route shapes and the 403/404 fallback; the final-gating requirement and the README both state the backend `mode:'results'` behavior and the frontend "View series detail" substitution. No divergence between spec and implementation was found.
