# Per-game detail accordion with line score, pitchers, and venue (v1)

Issue #19 extends the series detail page from a bare final-score line to a per-game accordion that, on expand, fetches inning-by-inning R/H/E, winning/losing/save pitchers, venue, and an optional MLB highlight from the Stats API. The backend adds a third Lambda (`GET /game?gamePk=`) backed by a cache-first service: a DynamoDB hit short-circuits the fetch, a miss fetches linescore + feed/live in parallel plus a best-effort content highlight, and the result is cached with a TTL chosen by game state (one week for completed, 60s for in-progress). Upstream failure returns a documented `{status:'unavailable'}` at HTTP 200 (never cached) so the UI keeps the already-known final score. The pure parsers tolerate missing fields, the new Lambda carries no Bedrock env or IAM, and all three acceptance criteria are covered by unit + e2e tests that would fail if the behavior were reverted.

Watch for: a React duplicate-key collision in the inning table when the MLB linescore omits `num` on more than one inning — defensive-path only, not reachable with real data (likely). Everything else checks out.

**Verdict**: APPROVED

## High-level view

The cache-first resolution in `getGameDetail` genuinely satisfies criterion 1: the cache hit returns before any fetcher is touched, and only the `ok` variant is written back, with the TTL branched on `isCompletedGameState`. The `unavailable` fallback is returned without a write, so a transient upstream outage never poisons the cache.

The failure contract is consistent end to end. The service swallows linescore/feed-live rejection into `unavailable`, the content highlight is isolated in its own try so it can never fail the whole call, the handler returns both union variants at 200 (only a thrown error becomes 500), and the frontend collapses both a rejected fetch and an `unavailable` body into the same inline note while leaving the final score visible — criterion 2.

The API surface is one route, `GET /game?gamePk=`, validated by `parseGamePk` (positive integer only, `400` otherwise). The new `GetGameDetailFn` is correctly scoped: `TABLE_NAME` only, no `BEDROCK_MODEL_ID`, no `bedrock:InvokeModel` grant, with a dedicated infra test asserting the Bedrock-env count stays at two.

The mobile scroll (criterion 3) is handled by wrapping only the table in an `overflow-x:auto` container, so the table scrolls while the page keeps its 375px no-overflow guarantee; an e2e test asserts both halves. Accordion accessibility (`aria-expanded`/`aria-controls`, `scope` on header/row cells, `role="region"` panel) is in place, and EN/JA i18n is at parity.

### Cache-first resolution and TTL-by-state

The cache hit returns before the `Promise.all` over the fetchers is constructed, so the "skip the fetch" behavior is structural; the test asserts all three fetchers and `putCachedGameDetail` are untouched on a hit. The best-effort content fetch is isolated in its own try/catch so a content outage degrades to "no highlight" rather than failing the call.

TTL selection branches on `isCompletedGameState(detail.gameState)`, which normalizes case/whitespace and matches `final`, `completed early`, and `game over`; everything else (including `Live`/`Preview`) gets 60s. Feed/live normally emits only `Final`/`Live`/`Preview`, so the extra two states are belt-and-suspenders and don't misclassify a live game as completed.

Note the asymmetry: `getCachedGameDetail` returns whatever is stored, while `putCachedGameDetail` is called only for the `ok` variant — so a cached `unavailable` cannot exist, and a transient upstream outage never poisons the cache.

### Defensive parsers against real MLB shapes

The three parsers are side-effect-free and each tolerate the omissions that actually occur in Stats API payloads. `parseLinescore` maps a missing `innings` array to `[]`, and each missing run/hit/error to `null` via `num()` (which also rejects `NaN`/`Infinity`), so the UI can distinguish a real `0` from unknown. `parseGameMeta` omits `venue` when blank and omits any absent decision — importantly `save`, which is frequently missing even on finished games. `parseHighlight` returns `undefined` (never throws) when the recap block or its URL is absent, and falls back to the URL as the title when the headline is missing.

One defensive-path wrinkle: a missing `inning.num` becomes `0`. The header and both body rows key their inning cells on `inning.inning`, so two innings each missing `num` would both key on `0` and trip React's duplicate-key warning. Real linescores always carry `num`, so this isn't reachable in production, but keying on the array index would eliminate the latent issue.

### Failure contract from handler to UI

The handler maps only a *thrown* error to 500; both union variants return 200, so `unavailable` is deliberately not an error path. `parseGamePk` rejects missing, empty, non-numeric, zero, negative, and decimal inputs (regex `^\d+$` plus a `> 0` check), each yielding 400; the handler test exercises `abc`, `0`, `-5`, and `1.5`.

On the frontend, `getGameDetail` intentionally has no seed fallback (unlike `getBracket`): a transport/HTTP failure throws so the caller's `.catch` can drive the fallback. The lazy fetch is guarded by `detailState.status === 'idle'`, so a settled `ready`/`fallback` state is sticky and re-expanding never refetches. Both a rejected promise and a resolved `status:'unavailable'` land in the single `fallback` state — the two render tests both assert the final score survives and no table renders.

### Infra scoping of the new Lambda

`grantReadWriteData` is applied to the new function but the `bedrock:InvokeModel` policy remains on `getPredictionFn` alone. The stack test was split so one case asserts exactly two functions carry `BEDROCK_MODEL_ID`, which would fail if the game-detail function ever picked up the model env — a regression guard, not just a presence check.

### Mobile horizontal scroll without page overflow

Only the table is wrapped in `.detail__linescore-scroll` (`overflow-x:auto`, `max-width:100%`), so the inning table scrolls horizontally on a narrow viewport while the surrounding layout is unaffected — the design that preserves the 375px no-overflow guarantee from prior issues. The e2e test sets a 375px viewport, expands a game, asserts the scroll container is scrollable (content overflow or `overflow-x` auto/scroll), and independently asserts `documentElement.scrollWidth <= innerWidth + 1` so a regression that pushed the page into horizontal overflow would fail.

### Test coverage

The backend covers the cache-hit short-circuit, long-vs-short TTL by state, the uncached `unavailable` fallback, and the content-failure-still-ok path; the parser suite covers present/missing/empty inputs for all three parsers including the missing-save and url-as-title cases. The handler suite covers 400s and the 200 `ok`. The frontend covers lazy-no-fetch-until-expand, fetch-once, table/pitchers/venue render, save-omitted, and both failure variants; the e2e suite covers ok render, the error note with surviving score, and the 375px scroll. These assert behavior (fetch counts, TTL constants, aria state, overflow math) rather than DOM shape, so they would fail if the feature were reverted.

Not tested: the duplicate-key defensive path (missing `num` on multiple innings) — consistent with it being unreachable with real data.

### Regression surface for prior issues

The game-time rendering from #20 (`localTime`) is preserved, now rendered inside the toggle button rather than a bare span. The favorites (#18) and auto-refresh (#17) paths are untouched by this diff. The new styles are namespaced under `.detail__game*`/`.detail__linescore*` and don't alter existing selectors.
