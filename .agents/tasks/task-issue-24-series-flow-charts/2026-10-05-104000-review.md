# Series-flow visualization: SVG charts, probability overlay, and bracket sparkline (v1)

Issue #24 adds a "series flow" view: on the series detail page, a per-game run-differential bar chart and a cumulative series-win trend chart, plus — for the predictable current season — an overlaid per-game predicted win-probability trend; and on each bracket card, a small score-difference sparkline. The implementation is frontend + docs only, with one additive shared export: the per-game truncation that the backtest already performed was lifted into a new `seriesProbTrend(series, bracket, accuracy)` in `shared/src/backtest.ts`, and the frontend's `winProbTrend` delegates to it, so the pure `predict()` stays the single probability source. Every chart is an inline SVG (`role="img"` with an accessible name) paired with a collapsible real `<table>` that conveys the same numbers in text, winner included as text. Charts use team brand colors for data marks and theme CSS variables for axes/labels so they stay legible in dark mode.

Watch for: the probability overlay's `predictable` prop can only *suppress* the overlay, never force it on — the render guard ANDs it with `isPredictable(season)` regardless (confirmed, by design but worth noting). The sparkline's screen-reader summary prepends `+` unconditionally, so a no-winner / in-progress game reads as `- +0` (confirmed, minor polish). No blocking issues found.

**Verdict**: APPROVED

## High-level view

The probability refactor is behavior-preserving. `sampleSeries` no longer owns the slice/recompute-wins loop; it calls `seriesProbTrend` and layers the eventual-winner scoring on top. The seed backtest numbers are unchanged (shared suite 37/37 green, `runBacktest(2024)` still pins 43 samples), and `seriesProbTrend` is exercised directly with a pinned in-progress case. This is the right shape: one truncation, one `predict()` caller, two consumers.

The tabular alternatives are genuine data mirrors, not decoration. Component tests read the rendered table cells back and assert they equal the pure-helper output exactly — winner as `DET won`, probabilities as `70% / 51% / 62%`, cumulative wins as integers. `aria-labelledby` points at the localized `<figcaption>` title and `aria-describedby` at the table container, both via a collisionsafe `useId`-derived base.

Acceptance criterion 2 is satisfied structurally, not just by test fixtures: `isPredictable` is `season === 2026`, so 2024/2025 seed seasons return the two base charts with no probability chart, which the e2e deep-link into a 2024 seed series confirms (`PROB_CHART` count 0). The overlay only appears for the predictable season with games.

Criterion 3 holds: bars are filled with `teamColor(winnerId).primary` and trend lines stroked per team; the probability line/dots use `--focus-ring`; all axes, ticks, frames, table borders, and backgrounds reference theme variables (`--border-strong`, `--surface-2/3`, `--muted`, `--ink`, `--heading`) that are defined for both light and dark palettes. No hardcoded colors in the chart CSS. On-bar numeric labels pick their foreground via `readableTextColor` against the team fill.

The sparkline adds zero tab stops. It is a single `role="img"` SVG with `aria-hidden` children and no focusable node; the SeriesCard regression test pins the card's interactive descendants at exactly three buttons and re-asserts the card's `tabindex="0"` and accessible name, so the #22 roving-tabindex model and #18 favorite highlight are untouched. CSS caps it at `max-width:100%` for the 375px no-overflow requirement.

<summary>Issues (2)</summary>

1. **Overlay prop is suppress-only** — `SeriesFlowCharts`' `predictable` prop is ANDed with `isPredictable(season)` in the render guard, so passing `predictable={true}` can never force the overlay on a non-predictable season; the prop only turns it off. Harmless today (the one caller passes `isPredictable(season)`), but the prop's doc comment reads as if it can enable the overlay. Consider dropping the redundant `&& isPredictable(season)` or renaming the prop to reflect that it gates-off only.
2. **Sparkline summary reads `- +0`** — `summarize` builds `${who} +${row.diff}`, so a game with no resolved winner and no margin is announced as `- +0`. Drop the `+` (or the whole token) when `winnerTeamId` is null so the screen-reader label doesn't claim a `+0` margin for an unplayed/in-progress game.

### `seriesProbTrend` as the single truncation, `sampleSeries` layered on top

The refactor moves the per-game loop — sort by `seriesGameNumber`, for each k build a partial series whose `games` are the first k and whose `high.wins`/`low.wins` are recomputed by `countWins` over those k games, set status `in_progress` for k<N else `final`, call `predict` — out of `sampleSeries` and into the exported `seriesProbTrend`. `sampleSeries` keeps its `status === 'final'` gate and its eventual-winner computation, then maps over the trend to attach `eventualWinnerTeamId` / `favoriteWasCorrect` / `probOfEventualWinner`. The eventual winner is still derived from the full `countWins` totals, independent of the per-k partials, so the backtest scoring is unchanged.

Two consumers now share one truncation: the backtest (final series only, with scoring) and the frontend trend chart (any series with games, no scoring). The key behavioral difference is deliberate and documented — `seriesProbTrend` does not require `final`, so an in-progress series yields a trend up to its latest played game. The shared test pins that: a single-game in-progress series returns `favoriteWinProbability: 0.697`.

Behavior-preservation is checked meaningfully rather than asserted. `backtest.test.ts` keeps `runBacktest(POSTSEASON_2024)` at `sampleCount` 43 and adds a loop asserting, for every final seed series, that `seriesProbTrend` yields one point per game in ascending order with probabilities clamped to [0.5, 0.95]. If `sampleSeries` had stopped delegating (e.g. drifted on how partial win counts are computed), these would diverge.

### Tabular alternatives carry the same data as each SVG

`ChartFigure` wires `aria-labelledby={titleId}` (the localized `<figcaption>`) and `aria-describedby={tableId}` onto the SVG, with a toggle button (`aria-expanded`/`aria-controls`) revealing a `<table>` carrying `scope="row"` game-number headers. The diff table conveys the winner **as localized text** (`{team} won` / `Tie` / `In progress`), never color alone; `winnerText` distinguishes an actual tie (both scored, equal) from an unplayed game, so the column stays correct for in-progress series.

The component tests render, open the table, read `getAllByRole('cell')` back, and assert exact strings (`['DET 3','HOU 1','2','DET won']`, `['NYM','70%']`) equal to the pure-helper output — real rendered-DOM verification, not a mocked table.

### Overlay gating and criterion 2

```
seasonPredictable = predictable ?? isPredictable(season)
showProb          = seasonPredictable && isPredictable(season) && series.games.length > 0
```

Because `isPredictable(season)` is re-checked in `showProb`, the overlay is strictly gated to the current season (2026) with at least one game. For 2024/2025 seed seasons the two base charts render and the probability chart and its "Favorite win probability" column are absent — asserted both in the component test (`queryByRole(... 'Predicted win probability by game')` not present) and the 2024 e2e deep-link (`PROB_CHART` count 0, after the base two are visible). The predictable path is covered by a 2026 in-progress fixture (component) and the stubbed 2026 FINAL ALCS (e2e), both showing all three charts and a `%` in the probability table.

The redundant `&& isPredictable(season)` is what makes the `predictable` prop suppress-only (see Issues). Not a correctness bug for the single current caller, but the prop semantics in the doc comment overstate what it can do.

### Team color + dark-mode legibility

The one text-on-fill case (the on-bar diff number) computes contrast via `readableTextColor(teamColor(...).primary)`, with a `var(--surface)` fallback for neutral bars. I grepped the chart CSS for hardcoded hex and found none — every axis/tick/frame/surface/table color resolves to a theme variable that `styles.css` defines in both the light root and the dark override. A dark-mode full-page screenshot is captured in the e2e for manual legibility review.

### Sparkline: no new tab stop, no regressions

The SeriesCard regression test pins exactly three interactive descendants (two favorite toggles + games toggle) with the sparkline present, plus the card's `tabindex="0"` and its team-name `aria-label` — so the sparkline adds no tab stop and the #22 roving-tabindex / Enter-Space model and #18 favorite highlight are untouched. `.series-card__sparkline { max-width:100% }` with a fixed 18px height holds card heights and prevents 375px overflow.

The `aria-label` summary (`summarize`) is the sparkline's only text channel, and it prepends `+` unconditionally — fine for a decided game (`DET +2`), misleading for a no-winner game (`- +0`). See Issues.

### Pinned numbers are load-bearing

The helper tests pin full objects, not shapes: the sweep trend `0.6928 / 0.7839 / 0.8333` and the seven-game close series probabilities would all change if the truncation or recompute-wins logic regressed, and the in-progress case pins that game 2 (null scores) reuses game 1's win counts rather than inventing a win. The cumulative-trend test deliberately stores "wrong-looking" final win counts in the fixture and asserts the recomputed-from-`isWinner` running totals, guarding the "don't trust stored wins" contract shared with `countWins`.

### Docs

Both READMEs gain a parallel "Series-flow visualization" section (EN/JA in sync) and the spec files are updated. Each claim checks out against the code — frontend-only, overlay reuses pure `predict()` via `seriesProbTrend` (no Bedrock/live calls), winner-as-text, dark-mode theme variables, sparkline with no tab stop / no overflow — with no overstated claims.
