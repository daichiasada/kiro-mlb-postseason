# MLB postseason summary site: graphical bracket, deterministic prediction, Bedrock narrative, one-command CDK deploy (v1)

A greenfield npm-workspaces monorepo that renders the 2024 MLB postseason as a graphical bracket and adds a per-series win/loss prediction. The backend aggregates the public MLB Stats API into a `Bracket`, computes a favorite with a transparent in-code heuristic (probability clamped to `[0.5, 0.95]`), and asks Amazon Bedrock to turn that number into a short narrative, falling back to a deterministic template on any Bedrock error so the endpoint never hard-fails. The frontend is a React/Vite SPA served from private S3 behind CloudFront, pointed at the API via a deploy-time `/config.js`; the whole stack (DynamoDB cache, two Node 20 Lambdas, HTTP API, Bedrock IAM) is one CDK app with one-command deploy. All approved stack choices are honored, auth is intentionally absent, real SVG assets are committed, and Kiro University rules are captured as always-on steering.

Watch for: the frontend-to-backend **series-ID contract** — predictions are requested by a series ID the frontend may have gotten from the bundled seed, while the backend may compute IDs from live MLB data; a mismatch yields a 404 (likely). The Bedrock prompt/response path cannot be exercised offline, so the only verification is the mock and the fallback (confirmed). `infra/` ships no tests, so the CDK wiring is covered only by `synth` (confirmed).

**Verdict**: APPROVED

## High-level view

Pure logic is separated from I/O: `aggregateBracket` and `predict` are pure functions, while MLB fetch, DynamoDB, and Bedrock sit behind injectable interfaces on `BracketService`. That seam is what makes the suite runnable without AWS.

The prediction is two-layered: a deterministic, unit-tested heuristic owns the number, and Bedrock only produces prose. The AI path degrades on any failure to a templated narrative tagged `(fallback)` in the `model` field — a fail-open choice that keeps the degradation observable in the response.

The frontend resolves series by exact string ID, which couples the two sides tightly: the ID the UI holds must match the ID the backend derives for the same series. When the UI is showing seed data but the backend is live (or vice versa), that assumption can break and the prediction 404s.

Resolution order is cache → live MLB → 2024 seed on the backend, and live API → seed on the frontend; both fall back to the same bundled dataset. The seed covers the full 11-series 2024 bracket through a Dodgers–Yankees World Series.

The CDK wiring matches the approved architecture, with Bedrock `InvokeModel` scoped to foundation-model/inference-profile ARNs in-region rather than `*`. Known gaps: no infra tests, and the frontend/backend ID coupling noted above.

### Pure core behind injectable I/O

The network (`fetchPostseasonSchedule`), cache (`BracketStore`), and AI (`BedrockInvoker`) are all constructor-injected on `BracketService` with real implementations as defaults, so the service tests drive cache-hit, cache-miss-then-aggregate-and-store, MLB-failure-to-seed, and no-seed-rethrow with in-memory doubles.

Aggregation groups games by `(seriesDescription + unordered team pair)`, assigns the high seed from the game-1 home team, and derives status from the clinch count `ceil(bestOf/2)`. The design choice that carries risk: `mapRound` falls back to `Division Series` on an unrecognized description and `mapLeague` falls back to `WS`, so upstream schema drift produces a best-effort bracket instead of a thrown error — a malformed round silently lands in the wrong column rather than failing loudly.

### Prediction favors live results, with a transparent blend

The heuristic blends series progress (weight 0.7) with regular-season win pct (weight 0.3, neutral 0.5 when unknown) plus a 0.02 home-field edge for the high seed, then normalizes to the favorite's share and clamps to `[0.5, 0.95]`. For a completed sweep the progress term dominates and the model favors the actual winner even when it is the low seed (DET over HOU in the seed data), which the service and model tests both assert. The `winPct` map is the only non-trivial signal left unwired in production — it is always `{}` outside tests — so today the number is effectively driven by series progress and the home-field tiebreaker alone. That is fine for the stated scope but worth knowing: a yet-to-start series (0–0) always resolves to the high seed at the clamp floor of 0.5-ish, not a data-driven call.

### Bedrock isolation and fail-open narrative

```
generateNarrative ─▶ invoker.invoke(modelId, prompt)
                        │ success ─▶ { narrative, model: modelId }
                        └ throw ───▶ { narrative: fallbackNarrative(...), model: `${modelId} (fallback)` }
```

The real invoker builds an Anthropic `messages` body (`anthropic_version`, `max_tokens`, `temperature`, text content), decodes the response, and concatenates `content[].text`, throwing if empty. None of this request/response shaping is exercised against anything real — the test mocks `invoke` and asserts the fallback on throw. A wrong body shape, a region without model access, or an SDK response change would only surface at deploy time. The `(fallback)` suffix on `model` makes the degraded path observable in the API response; a single post-deploy smoke test would close the remaining risk.

### API surface and the series-ID contract

`GET /bracket?season=YYYY` returns the bracket; `GET/POST /prediction` take `seriesId` plus optional `season`. `parseSeason` enforces a 4-digit year (default 2024) and 400s on anything else; POST additionally 400s on non-JSON bodies; a missing series is 404 via `SeriesNotFoundError`; everything else is a 500 with a generic message.

The coupling to watch is the series ID. `getPrediction` resolves the series by exact string match against `bracket.series`. The frontend obtains that ID from whichever bracket it rendered — which may be the **bundled seed** when the live API was unreachable — and then sends it to the backend, which independently resolves its own bracket (cache → live MLB → seed). If the frontend is on seed data while the backend reaches live MLB, the two IDs must be byte-identical. They are built from `${season}-${league}-${slug}-${highId}-${lowId}`, where high/low come from the game-1 home team; any disagreement in seed assignment between the hand-authored seed and the live aggregation produces a 404 on an otherwise valid click. Resolving predictions by round + unordered team pair would decouple the two sides; at minimum, the live-vs-seed IDs for 2024 should be confirmed equal.

### Backend/frontend fallback symmetry

Both layers fall back to the same 2024 seed, but with different visibility. The frontend flags `usedFallback` and renders an offline notice; the backend substitutes the seed silently inside `getBracket` with no signal in the payload. So a client cannot tell whether a 200 bracket is live or seed data — only the prediction's `model` field hints at degradation, and only for the Bedrock leg. Prediction failures on the frontend are surfaced to the user with no silent fallback.

### CDK wiring: least-privilege Bedrock, SPA routing, config injection

Private S3 (`BLOCK_ALL`, OAC, enforced SSL), CloudFront routing 403/404 to `/index.html` for SPA deep-links, HTTP API CORS locked to the distribution domain plus two localhost origins, and the Bedrock policy granting `InvokeModel`/`InvokeModelWithResponseStream` scoped to `foundation-model/*` and `inference-profile/*` in-region on the prediction function only — genuine least-privilege for the AI path. The `/config.js` injection points a prebuilt bundle at a per-deploy API URL, loaded before the app bundle in `index.html`.

Two wiring notes. The prediction Lambda gets `grantReadWriteData` on the table even though its only write path is the shared `getBracket` cache-fill; that follows from reusing `BracketService` but is broader than the handler strictly needs. And `DeploySpa` prunes by default while `DeployRuntimeConfig` uses `prune:false` to preserve the SPA files — the ordering writes `/config.js` after the SPA, but a redeploy's prune step on the first deployment can transiently remove a prior `/config.js` before the second rewrites it; worth confirming the deployment dependency guarantees the file is never absent.

### Tests exercise the real paths, except infra

Backend tests hit the real `aggregateBracket`, `predict`, `buildPrompt`, `fallbackNarrative`, and the `BracketService` orchestration with mocked collaborators — these are the behavior-bearing paths, and the mocks are at the I/O boundary, not over the logic under test. Frontend tests cover `bracketLayout`, `SeriesCard`, and `PredictionPanel` (including loading/error/success states). What is not tested: the `infra/` stack has no assertions (only `synth`), the real `RealBedrockInvoker` request/response shaping, and the live MLB client (`fetchPostseasonSchedule`) — all three are the pieces that only run against AWS/HTTP, so the gap is understood but real.
