### Specs trace to the real system, not a hypothetical one

`design.md` describes the `getBracket` resolution order as cache → live fetch+aggregate+cache → 2024 seed on failure, and `getPrediction` as resolve-series (exact id, then round-slug + unordered team-pair) → `predict` → `generateNarrative` with deterministic fallback. That matches `bracketService.ts` exactly, including the ISSUE-1 unordered-pair fallback in `resolveSeries` and the `${season}-${league}-${roundSlug}-${highId}-${lowId}` id grammar parsed from both ends. The aggregation section correctly states the `(seriesDescription + unordered pair)` grouping, home-team-of-game-1 as high seed, and the `ceil(bestOf/2)` clinch rule for `final`. The prediction section states the 0.7/0.3 progress/strength blend, the 0.02 home-field edge, and the `[0.5, 0.95]` clamp — all present in `model.ts`.

### Property tests assert real invariants that would catch violations

`model.property.test.ts` drives the real `predict` with distinct team ids, best-of in {3,5,7}, win counts bounded by clinch, and (in the third property) a randomized win-pct map in [0.3, 0.7]. It asserts `favoriteWinProbability ∈ [0.5, 0.95]` and that the favorite is one of the two teams. These are not trivially true: with win-pct as low as 0.3 the raw favorite share can dip below 0.5, so the lower clamp is actually exercised — removing the clamp in `model.ts` would fail the suite. A determinism property is included as well.

`aggregate.property.test.ts` builds raw games whose away/home winner is internally consistent (`isWinner: awayWin` / `!awayWin`), caps the generated game count at `gamesInSeries`, and flattens 1–4 series into one call. It asserts each series' `high.wins`/`low.wins` stay within `[0, bestOf]` and that `status`/`league`/`round` fall in their valid enums. A win-tally bug or a bad `mapRound`/`mapLeague` default would surface here.

One note: the real upper bound on wins is the clinch count `ceil(bestOf/2)`, not `bestOf`, so `wins <= bestOf` leaves a gap — an over-count between clinch+1 and bestOf would pass. Tightening to the clinch bound would make the invariant match the code's actual contract. Optional.

### Hooks, MCP, and custom agent are coherent and well-formed

The three `*.kiro.hook` files use the `enabled / name / description / version / when / then` shape. `run-tests-on-save` fires on `backend/**` and `shared/**` and asks for `npm test -w @mlb/backend` including the property tests; `typecheck-on-save` fires on any `.ts`/`.tsx`; `run-e2e-suite` is a `userTriggered` manual hook disabled by default because it needs a browser. Every targeted path and command maps to a real workspace script.

`mcp.json` wires `aws-docs` (`uvx awslabs.aws-documentation-mcp-server@latest`) and `fetch` (`uvx mcp-server-fetch`) with narrow `autoApprove` lists and no embedded secrets — appropriate for a trust boundary that reaches public docs and the public MLB Stats API. The packaged power's `mlb-fetch` server reuses the same public `mcp-server-fetch` and bundles no credentials.

`mlb-postseason-dev.json` encodes the monorepo layout, test-first conventions, the exact `getBracket`/`getPrediction` resolution order, the clamped probability, and the Bedrock fallback. Its `allowedCommands` and `context.steering`/`context.specs` arrays reference files that all exist, and the `-w @mlb/frontend`/`@mlb/backend` targets match the real package names — a real, usable agent definition rather than a stub.

### Packaged power is self-contained and build-neutral

`powers/mlb-postseason/` carries a `power.json` manifest (steering + skill + `mlb-fetch` MCP server), a bundled `steering/mlb-stats-api.md`, a `skills/aggregate-bracket.md`, and a README. It sits outside the `workspaces` glob (`shared`, `backend`, `frontend`, `infra`), so it is a non-built asset and cannot affect `npm run build`/`test`/`synth` — the README states this explicitly and it checks out against the root `package.json`. The skill points at `backend/src/mlb/aggregate.ts` as the source of truth, keeping the packaged artifact tied to real code.

### Stale university steering undersells the submission

`.kiro/steering/kiro-university.md` is `inclusion: always`, so Kiro (and a curious judge) reads it on every task. It was written early in the build and still says "Agent hooks **potential**", "hooks ... **can be added** without rework", and its "How this project demonstrates the lessons" list covers only spec/steering, Bedrock, IaC, testing, and docs — it never mentions the now-shipped hooks, MCP config, packaged power, custom agent, or property-based testing. `DEMONSTRATED_LESSONS.md` is the authoritative judge-facing map and is accurate, so this is not blocking, but the stale steering reads as weaker than the actual submission. Refreshing it to past tense and adding the four lessons it omits would remove the discrepancy.
