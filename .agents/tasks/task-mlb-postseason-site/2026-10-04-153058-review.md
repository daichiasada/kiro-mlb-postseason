# Autonomous resolution of the four v1 issues plus mobile e2e hardening (v2)

The two features that landed since v1 close out the issues the first review raised rather than add product surface. FEAT-006 resolves the series-ID coupling with a round-plus-team-pair fallback in `BracketService`, adds a `RealBedrockInvoker` request/response unit test, adds `aws-cdk-lib/assertions` tests over the CDK stack, and collapses the two-step `/config.js` deployment into a single `BucketDeployment`; it records all of this in a tracked `ISSUES.md` registry. FEAT-005 adds a Playwright e2e suite that drives the real SPA (offline seed fallback + stubbed prediction endpoint) and fixes a confirmed mobile bracket overflow with a `<=560px` media query. All four v1 issues are genuinely addressed, the core requirements still hold, and the suite is green (43 unit + 7 e2e).

Watch for: the CDK Lambdas target `nodejs20.x`, which synth now flags as deprecated (creation disabled 2027-02-01) — a real deploy-horizon concern, not present at v1 (confirmed). The ISSUE-2 live Bedrock smoke test remains deliberately deferred and un-run (confirmed, accepted trade-off). The series-ID fallback matches on round-slug + team pair and intentionally ignores the `league` and `season` id segments; safe given the bracket is season-scoped and a team pair is unique, but worth knowing (confirmed).

**Verdict**: APPROVED

## High-level view

The series-ID fix is sound. `resolveSeries` tries an exact id match, then parses the requested id from both ends (team ids are the trailing two segments, slug is whatever sits between league and the ids) and matches a stored series by round slug plus the *unordered* team pair. A swapped high/low order resolves; a wrong team pair still throws `SeriesNotFoundError`. Both branches are tested. The echoed-back `seriesId` is the client's requested string, not the resolved one — cosmetic, callers key off team/probability fields.

The infra assertion tests meaningfully guard the stack. They synthesize in-process with a fixed env (no AWS call) and assert the properties that matter for regressions: DynamoDB TTL on `ttl` + `pk` hash key, exactly two `nodejs20.x` application Lambdas carrying `TABLE_NAME`/`BEDROCK_MODEL_ID`, an IAM policy allowing `bedrock:InvokeModel`, the three HTTP routes, CloudFront 403/404→`/index.html`, and exactly one `Custom::CDKBucketDeployment`. These would fail on the regressions they target.

The single-BucketDeployment change truly removes the prune race. The SPA asset and the `config.js` `Source.data` are now one managed object set under one deployment, so prune can never transiently drop `/config.js`; the assertion pins the deployment count at one, and synth confirms the config content still ships.

The Bedrock shaping test exercises the real `RealBedrockInvoker` path by injecting a stubbed `BedrockRuntimeClient`: it asserts the `InvokeModelCommand` input (modelId, contentType/accept, Anthropic `messages` body with `anthropic_version`/`max_tokens`/`temperature`) and the `content[].text` parse/concat/empty-error branches. The one gap it cannot close — that the live endpoint accepts this body — is explicitly logged as a post-deploy smoke test.

The Playwright specs drive real UI behavior through the production preview build: image-asset/alt-text checks, the offline-fallback notice, all four rounds + AL/NL/WS lanes, the Dodgers-over-Yankees 4-1 WS card, the accessible prediction progressbar with stubbed success/error, and a 375px overflow guard asserting `scrollWidth - clientWidth <= 1`. The mobile fix backing that guard collapses the grid to one column and lets long names wrap.

The one new concern is the `nodejs20.x` runtime deprecation surfaced by synth. Everything else — graphical bracket, prediction, Bedrock + fallback, approved stack, no auth, real SVG assets, one-command deploy, always-on Kiro University steering — is unchanged from the v1 APPROVED state.

### Series-ID fallback: parse-from-both-ends, pair-scoped match

The fix lives entirely in `BracketService` and leaves the id format untouched. `parseSeriesId` splits on `-`, takes the trailing two segments as the team ids (rejecting non-finite values), the first as season, the second as league, and joins the middle as the round slug — which is correct precisely because the slug is pre-stripped of non-alphanumerics in `aggregateBracket.toSlug`, so it never reintroduces a hyphen. `resolveSeries` then matches by `roundSlugOf(series)` equality plus the sorted team-id pair, so `2024-al-wildcard-116-117` resolves the stored `2024-al-wildcard-117-116`.

The match deliberately ignores the parsed `season` and `league`. Season is implicitly correct because the bracket was already loaded via `getBracket(season)`; league is redundant because an unordered team pair uniquely identifies a matchup within a season — two series in the same round slug across AL and NL cannot share a team pair. The pair-scoped (not round-wide) matching is what keeps `2024-al-wildcard-200-201` throwing `SeriesNotFoundError`, and that negative case is tested alongside the swap case, so an over-broad match that resolved the wrong series would fail the suite.

### Infra assertions pin the resources that matter

```
Template.fromStack(stack)  // in-process synth, fixed env, no AWS call
  ├─ DynamoDB: TTL on `ttl` + `pk` HASH
  ├─ 2× nodejs20.x Lambda w/ TABLE_NAME + BEDROCK_MODEL_ID
  ├─ IAM policy: Allow bedrock:InvokeModel
  ├─ Routes: GET /bracket, GET /prediction, POST /prediction
  ├─ CloudFront: 403→/index.html, 404→/index.html (200)
  └─ Custom::CDKBucketDeployment ×1
```

The two-Lambda assertion uses `resourcePropertiesCountIs` matched on runtime + env rather than a raw function count, which correctly sidesteps CDK's synthesized helper Lambdas (bucket-deployment handler, auto-delete) — a naive `resourceCountIs('AWS::Lambda::Function', 2)` would have been brittle and wrong. The IAM assertion matches the action inside the policy document rather than asserting the exact resource ARNs, so it guards "InvokeModel is granted" but would not catch a regression that widened the resource scope from the foundation-model/inference-profile ARNs back to `*`; that is a smaller gap than v1 (which had no assertion at all) and acceptable, but noting it since the ARN scoping was called out in v1 as the genuine least-privilege win.

### Bedrock shaping test exercises the real invoker

The ISSUE-2 describe block constructs `RealBedrockInvoker` with an injected client whose `send` is stubbed to return an encoded Anthropic body — so the real `invoke` builds the command and parses the response, only the transport is faked. It asserts the command is an `InvokeModelCommand` with the right `modelId`/`contentType`/`accept`, that the body carries `anthropic_version: 'bedrock-2023-05-31'`, `max_tokens: 300`, a numeric temperature, and a single user message with text content, and that the parser extracts a single block, concatenates multiple blocks, and throws on empty content. This covers the exact mismatch classes v1 worried about (wrong body shape, response-parse drift). The residual — that the deployed region/model actually accepts the body — is logged in `ISSUES.md` as a one-time post-deploy curl and left un-run by design, since AWS credentials are inactive here.

### Playwright drives real UI, offline and stubbed

The suite runs against `vite preview` of the production bundle, not a dev mock. `home.spec` covers the brand/hero SVG assets and asserts no `<img>` lacks alt text, the offline-fallback notice (the backend is absent so `getBracket` falls to the seed), all four round headings and the AL/NL/WS legend images, and the WS card's Dodgers-over-Yankees 4-1 meta. `prediction.spec` stubs `**/prediction*` per-test with `page.route`, then asserts the favorite name, an accessible `progressbar` with `aria-valuenow`/min/max and a `68.0%` label on success, and a visible `alert` with "could not load prediction" on a 500. These exercise behavior-bearing UI (ARIA roles, fallback branch, error branch), not DOM trivia.

One test-quality note, not a defect: the hero assertion in the app-shell test uses `toHaveCount(1)` rather than `toBeVisible()`, so a hero that rendered but was hidden would still pass — minor, and the mobile spec separately screenshots the hero region.

### Mobile overflow fix is targeted and verified

The `<=560px` media query collapses `.bracket__grid` to a single column (overriding the `<=860px` two-column rule with `!important`), stacks the header, makes the hero full-width, and adds `min-width: 0` + `overflow-wrap: anywhere` so long team names wrap instead of forcing the row wider than the viewport. The e2e overflow guard measures `documentElement.scrollWidth - clientWidth <= 1` at 375px, which is the right invariant — it catches real horizontal overflow regardless of which element causes it, so a future wide element would re-trip it. The fix addresses the root cause (the retained two-column grid) rather than masking it with `overflow-x: hidden`.

### Core requirements re-confirmed

Nothing in these two features regressed the v1 baseline: the graphical bracket, the clamped deterministic prediction, the Bedrock narrative with observable `(fallback)` degradation, the approved S3+CloudFront / HTTP API+Lambda / DynamoDB / Bedrock-IAM stack, the intentional absence of auth, committed real SVG assets, one-command CDK deploy, and the always-on `.kiro/steering/kiro-university.md` (plus product/tech/structure) are all intact. The steering file maps the build to the required lessons (spec/steering-driven dev, hooks potential, Bedrock/MCP-style AI integration, IaC, testing, docs); hooks and property-based tests remain described-as-potential rather than materialized, which is a submission-completeness consideration for the orchestrator, not a code defect in these diffs.
